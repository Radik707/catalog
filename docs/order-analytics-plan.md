# План: аналитика заказов и рекомендации

> Черновик архитектуры. Статус: на согласовании. Дата: 2026-06-25.
> Связано с видением продукта (ветка «→ аналитика»), каналом заказов MAX и SQLite на daniella.

## 0. Цель
Собирать данные о заказах клиентов, показывать **аналитику в админ-панели** и со временем
давать **рекомендации к следующим заказам**. Делаем поэтапно: каждый этап самостоятелен и
полезен сам по себе, следующий навешивается сверху.

**Главный принцип:** аналитика начинается со сбора. Сначала тихо копим каждый заказ в
постоянное хранилище — анализ и рекомендации строятся уже поверх накопленного.

---

## 1. Что собираем (модель данных)

Три таблицы в SQLite на daniella (та же база, что и заказы MAX, — отдельным набором таблиц).

### `customers` — клиенты
| поле | смысл |
|---|---|
| `id` | внутренний id (autoincrement) |
| `channel` | `max` / `telegram` |
| `ext_id` | id клиента в канале (MAX user_id; для Telegram — пусто, см. §3) |
| `name` | имя |
| `contact` | профиль/телефон, если есть |
| `first_order_at`, `last_order_at` | первый и последний заказ |
| `orders_count` | счётчик заказов |

`UNIQUE(channel, ext_id)` — один клиент = одна запись.

### `orders_history` — заказы (шапка)
| поле | смысл |
|---|---|
| `id` | id заказа (тот же короткий id, что уходит боту) |
| `created_at` | когда собран в корзине |
| `channel` | `max` / `telegram` |
| `customer_id` | ссылка на `customers` (может быть пусто до опознания) |
| `total` | сумма заказа |
| `items_count` | число позиций |
| `state` | `pending` → `delivered` → `cancelled` |
| `delivered_at`, `cancelled_at` | метки времени переходов |

### `order_items` — позиции заказа (строки)
| поле | смысл |
|---|---|
| `order_id` | ссылка на заказ |
| `product_id`, `name` | товар |
| `price`, `qty`, `line_total` | цена, количество, сумма строки |

> Ключевое отличие от текущего: сейчас заказ хранится **текстом** (для сообщения боту).
> Для аналитики нужен **структурированный** список позиций — значит витрина при отправке
> заказа будет слать не только готовый текст, но и массив позиций `[{id,name,price,qty}]`.

## 2. Где храним
**SQLite на daniella** (файл рядом со службой загрузчика, как `max_orders.db`).
- Для нашего объёма (десятки заказов в день) — с запасом на годы.
- Ноль новой инфраструктуры: SQLite встроена в Python.
- Постоянное хранение (без TTL, в отличие от «рабочей» таблицы доставки).
- Postgres/облачная БД — избыточны; перейдём, только если реально перерастём (не скоро).

---

## 3. Как собираем (точки сбора)

### MAX (уже почти готово)
- `POST /max/order` уже принимает заказ. Расширяем payload: добавляем структурированные позиции.
- На `/max/order` пишем строку в `orders_history` (state=pending) + `order_items`.
- На `bot_started` (клиент открыл бота) — **опознаём клиента**: создаём/обновляем `customers`,
  проставляем `customer_id`, `state=delivered`, `delivered_at`.
- На отмену — `state=cancelled`, `cancelled_at`, обновляем счётчики.

### Telegram (нужна доработка)
- Сейчас Telegram-заказ уходит прямо в чат (`t.me/...?text=`), сервер его **не видит**.
- Решение: при нажатии «Отправить в Telegram» витрина дополнительно тихо шлёт копию заказа
  на сервер (тот же приём, `channel=telegram`).
- ⚠️ **Ограничение:** в Telegram-сценарии сервер не узнаёт, *кто* клиент (нет бота, только
  ссылка владельцу). Поэтому Telegram-заказы пишутся как **обезличенные** (товары есть, клиент —
  нет). Полная привязка «кто заказал» в Telegram появится только с Telegram-ботом (он в планах).
  Вывод: чем больше заказов идёт через MAX, тем богаче данные — это совпадает с курсом
  «канал заявок Telegram → Max».

Идемпотентность: повтор записи по тому же `order_id` не плодит дубликат (INSERT OR IGNORE / upsert).

## 4. Кто обрабатывает и анализирует
На нашем масштабе — **без отдельного человека, без «дата-команды», без тяжёлого BI**:
- **Этап аналитики:** агрегаты считаются обычными SQL-запросами по требованию (когда открываешь
  страницу в админке) + при желании еженедельный скрипт по cron на daniella.
- **Этап ИИ (позже):** слой Gemini/Claude поверх истории — для умных рекомендаций и
  «бота-консультанта» из плана. ИИ читает историю клиента и подсказывает.

## 5. Аналитика в админ-панели (выбранный формат)
Новый раздел в существующей админке на daniella (`uploader/admin.py`, вход по `ADMIN_SECRET`).
Серверные эндпоинты отдают агрегаты (JSON), страница рисует таблицы и цифры.

**Сводка (за период: неделя/месяц):**
- Заказов, выручка, средний чек, доля отменённых.
- Разбивка по каналам (MAX / Telegram).
- Динамика по дням/неделям.

**Товары:**
- Топ по выручке и по количеству.
- Аутсайдеры (что почти не берут).

**Клиенты:**
- Список: кол-во заказов, сумма, последний заказ.
- «Спящие» — давно не заказывали (кандидаты на обзвон).
- Карточка клиента: его заказы + любимые товары.

(Графики — по желанию, но сначала достаточно аккуратных таблиц и чисел.)

## 6. Рекомендации к следующим заказам
По нарастающей. **Первое работает без всякого ИИ** — обычный SQL по истории:
- **«Повторить прошлый заказ»** — последний заказ клиента одной кнопкой.
- **«Ваши обычные товары»** — топ-N товаров клиента по частоте.
- **«Пора пополнить»** — товары, которые клиент брал регулярно, но давно не брал (по среднему
  интервалу между заказами).
- **«Популярное у магазинов»** — топ товаров по всем клиентам (для новичков без истории).

Где показывать: в корзине («Возможно, забыли:»), в боте MAX, или как подсказку тебе в админке.
**ИИ-слой (позже):** более тонкие подсказки и консультант в боте поверх той же истории.

## 7. Приватность (152-ФЗ)
Имя/телефон клиента — персональные данные. Для маленького B2B-инструмента риск низкий, но
правильно: хранить **у себя на сервере** (daniella, а не у третьих лиц), доступ к аналитике —
только по `ADMIN_SECRET`. При желании — короткая строка согласия на витрине. Не блокер, держим в голове.

## 9. Решения (согласовано 2026-06-25)
1. **Структурированный payload заказа** (массив позиций вместе с текстом) — ✅ ДА.
2. **Telegram-заказы собираем обезличенно сразу** (товары без клиента), MAX — полно — ✅ ДА.
3. **Хранение бессрочное** — ✅ ДА (объём ничтожен: заказ ~пара КБ, SQLite тянет миллионы строк).
4. **С какого этапа начинаем** — на усмотрение исполнителя (сеньор). Рекомендация: сперва
   мост загрузки прайсов в MAX (см. §10, снимает ежедневную рутину), затем Этап 1 аналитики
   (сбор) — обе фичи используют один и тот же бот + сервер, логично делать рядом.

## 10. Смежная фича: мост загрузки прайсов через MAX-бот
Оператору каждый день присылают прайсы (Excel) в MAX. Идея: оператор пересылает файлы
**боту**, бот сам запускает обновление каталога и отвечает «принято N файлов, обновлено X товаров».
Убирает ручной шаг «скачать → зайти на сайт загрузчика → загрузить».

**Как работает:**
- Оператор шлёт боту `.xlsx` (одним или несколькими файлами) → вебхук `message_created` с
  вложением типа `file`.
- Бот скачивает файлы в очередь загрузчика (`INCOMING_DIR`) и запускает **тот же безопасный
  конвейер**, что и сайт-загрузчик (`app.py`: бэкап → upload.py → при подозрительно малом числе
  товаров откат → архив). Никакой отдельной «сырой» загрузки — все защиты сохраняются.
- Бот отвечает оператору: «Принял N файлов, обрабатываю…», затем «✅ Каталог обновлён: X товаров»
  или «⚠️ вернул прошлую версию» / «❌ ошибка».

**Безопасность (критично):** принимать прайсы можно ТОЛЬКО от доверенных отправителей —
allowlist `MAX_UPLOAD_CHAT_IDS` (chat_id оператора и/или владельца). Любой другой, приславший
Excel, получает вежливый отказ и НЕ запускает обновление. Онбординг оператора: он один раз пишет
боту, ловим его chat_id из лога (как делали с владельцем), вносим в allowlist.

**Открытый техвопрос:** точная структура входящего вложения `file` (где `url`/`token` для
скачивания) — подтверждаем по реальному payload при внедрении (у MAX доки расходятся с практикой),
поэтому первый шаг реализации — логировать сырое событие с файлом.
