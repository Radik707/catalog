# Feature Research: Offline PWA для B2B-каталога торгового агента

**Domain:** Offline-first PWA catalog (B2B field sales, ~900 products, ~850 Cloudinary photos)
**Researched:** 2026-06-12
**Confidence:** HIGH (iOS/Android storage limits verified via WebKit blog + web.dev; caching patterns — официальный MDN + Workbox; UX patterns — отраслевые источники)

---

## Контекст: на что опирается это исследование

Существующий каталог (`catalog-khaki.vercel.app`) — Next.js 14 App Router на Vercel, ISR revalidate=300, данные из Google Sheets, ~900 товаров, фото в Cloudinary (два домена: `akkond/` и `presenter/`). Корзина в localStorage, заказ через Telegram deep-link. Двухуровневая навигация: 5 разделов → подгруппы. Сегодня — только online. Задача вехи v1.3: торговый агент обновляется **утром один раз**, весь день работает **без сети**.

Целевая платформа: **смешанный Android + iPhone** — это ключевое ограничение для всех UX-решений.

## Feature Landscape

### Зона 1: Установка и онбординг

#### Table Stakes (пользователь ожидает по умолчанию)

| Фича | Почему ожидается | Сложность | Зависимости от существующего |
|------|------------------|-----------|------------------------------|
| Установка как приложение (иконка на домашнем экране) | Каталог открывается каждый день — должен быть как приложение, не вкладка браузера | MEDIUM | Нужен `manifest.json`, иконки 192/512px, `theme_color` под синюю шапку каталога |
| **Android:** автоматический баннер установки («Добавить на экран») | Android Chrome показывает `beforeinstallprompt` — это бесплатная фича, агент ожидает увидеть | LOW | Обработать событие `beforeinstallprompt`, отложить его до нужного момента |
| **iOS:** встроенный баннер с инструкцией «Нажми Поделиться → Добавить на экран» | iOS Safari не поддерживает `beforeinstallprompt` — без баннера агент просто не знает как установить | MEDIUM | Определять iOS User-Agent, показывать кастомный bottom-sheet с иконкой Share и стрелкой вниз |
| Промпт установки появляется в правильный момент, а не сразу | Немедленный промпт раздражает и его игнорируют; показывать после того как агент открыл каталог и просмотрел хотя бы один раздел | LOW | Логика в `useEffect` + localStorage-флаг «промпт уже показан» |
| После установки — приветственный экран «Теперь обновите данные» | Агент только что установил, данных в кэше ещё нет — нужно направить к синхронизации | LOW | Логика: если кэш пустой → показать пустой state с кнопкой «Обновить каталог» |

#### Differentiators (выделяет продукт)

| Фича | Ценность | Сложность | Заметки |
|------|----------|-----------|---------|
| Кнопка установки внутри UI каталога (плавающая / в шапке) | Агент не следит за системными баннерами — если кнопка видна в самом приложении, конверсия установки выше | MEDIUM | Android: используем сохранённый `deferredPrompt.prompt()`; iOS: открываем инструкцию |
| Splash screen с лого «Вкусный Дом» при запуске | Нативное ощущение; без него — белый экран при запуске из home screen | LOW | `background_color` + `theme_color` в manifest, иконка маскируемая |

#### Anti-Features (кажутся хорошими, создают проблемы)

| Фича | Почему хочется | Почему нет | Вместо этого |
|------|---------------|-----------|--------------|
| Форсированный редирект «установи сначала» | Кажется, что повышает конверсию | Ломает доступ для клиентов (они открывают ту же ссылку в браузере); часть агентов не сможет обновить данные без установки | Мягкий промпт, каталог работает и в браузере |
| Промпт установки при каждом посещении | «Напоминать» кажется полезным | Раздражает агентов, которые уже отказались или не могут установить; iOS-агенты получат баннер снова и снова | Показать один раз, запомнить решение в localStorage |

### Зона 2: Офлайн-опыт (что работает / что деградирует)

#### Table Stakes (пользователь ожидает по умолчанию)

| Фича | Почему ожидается | Сложность | Зависимости от существующего |
|------|------------------|-----------|------------------------------|
| Весь список товаров доступен офлайн (9×100 позиций) | Это главная причина вехи; без этого смысл PWA нулевой | HIGH | `getProducts()` → API → Google Sheets: результат нужно кэшировать в IndexedDB или Cache API |
| Двухуровневая навигация работает офлайн (разделы → подгруппы) | Агент ориентируется по разделам — если навигация ломается без сети, каталог бесполезен | HIGH | `GROUP_ORDER`, структура групп должна быть в IndexedDB вместе с товарами |
| Поиск по названию работает офлайн | Агент часто ищет конкретный товар — ключевой сценарий в поле | MEDIUM | Поиск уже клиентский (filter в `CatalogView.tsx`) — работает автоматически при офлайн-данных |
| Фото доступны офлайн (хотя бы для просмотренных товаров) | Клиент магазина хочет видеть товар — без фото теряется треть ценности показа | HIGH | Cloudinary-URL в Cache API; стратегия — поэтапная загрузка (не все 850 сразу) |
| Корзина работает офлайн (добавление, просмотр, редактирование) | Агент набирает корзину прямо у клиента — без сети | LOW | Уже работает через localStorage; сохранится без изменений |
| Чёткий индикатор «ты офлайн» | Без индикатора агент паникует «каталог сломался»; с ним — спокойно работает | LOW | `navigator.onLine` + событие `offline/online`; цветная полоска или бейдж в шапке |
| Кнопка «Отправить заказ» деактивируется офлайн с пояснением | Telegram deep-link не откроется без сети — молчащий сбой хуже, чем явное предупреждение | LOW | `navigator.onLine` проверка в кнопке корзины; текст «Подключитесь к сети для отправки» |
| Страница «нет данных» если кэш пуст и сети нет | Лучше честный экран «Нет данных — обновитесь при наличии сети», чем пустая страница | LOW | Офлайн-fallback страница `/~offline` (поддерживается `@ducanh2912/next-pwa`) |

#### Differentiators (выделяет продукт)

| Фича | Ценность | Сложность | Заметки |
|------|----------|-----------|---------|
| Предзагрузка фото текущего раздела при переходе | Агент видит товары раздела без задержки; не нужно ждать, пока каждое фото прогрузится | MEDIUM | Service worker intercept + cache-first для Cloudinary, prefetch видимого экрана |
| Полноэкранный просмотрщик фото (lightbox) работает офлайн | Уже реализован lightbox — закэшированное фото должно открываться в нём же офлайн | LOW | Зависит от того, закэшировано ли фото — деградировать gracefully если нет |
| Режим презентации работает офлайн | Агент проводит показ клиенту — перебои сети не прерывают презентацию | LOW | Данные закэшированы; фото в режиме презентации — те же Cloudinary URL |

#### Anti-Features

| Фича | Почему хочется | Почему нет | Вместо этого |
|------|---------------|-----------|--------------|
| Кэшировать все 850 фото при первой установке | «Офлайн = все данные на телефоне» | **iOS: Cache API лимит 50 MB на раздел в браузере** (в standalone Home Screen — до 60% диска, но это нестабильно). 850 WebP по ~80KB = ~68 MB — на грани или за лимитом; плюс долгая первая синхронизация (3-5 мин на 4G) | Стратегия progressive caching: сначала кэшировать данные (JSON) + фото видимого/посещённого раздела, остальные — по мере навигации (cache-on-navigation) |
| Кэшировать всё в localStorage | Знакомый инструмент | localStorage синхронный, ограничен 5–10 MB, не предназначен для бинарных данных (фото) | JSON каталога → IndexedDB; фото → Cache API (Workbox) |
| Фоновая синхронизация без участия пользователя (Background Sync API) | «Само обновится когда появится сеть» | Background Sync на iOS не поддерживается до iOS 16+; Android — поддерживается, но непредсказуем в Chrome; для утренней синхронизации агент и так онлайн | Явная кнопка «Обновить каталог» — надёжнее и понятнее для пользователя |

### Зона 3: Флоу обновления (как агент получает новый каталог)

#### Table Stakes

| Фича | Почему ожидается | Сложность | Зависимости от существующего |
|------|------------------|-----------|------------------------------|
| Заметный баннер/тост «Доступно обновление каталога» | Агент должен знать что данные устарели; без сигнала — работает со вчерашними ценами | MEDIUM | Service worker `updatefound` + `postMessage` в страницу → показ баннера |
| Одна кнопка «Обновить сейчас» — скачивает новые данные + фото | Агент не технарь; действие должно быть очевидным и одним | MEDIUM | Кнопка запускает: fetch `/api/products` → сохранить в IndexedDB → обновить кэш изменившихся фото |
| Умная стратегия: не качать все 850 фото заново | Обновление ежедневное; при 850 фото full-refresh = 5+ мин и трата трафика | HIGH | Сравнить список `imageUrl` из нового JSON со старым → качать только появившиеся или изменившиеся URL |
| Обновление JS/CSS (service worker) применяется после перезагрузки, не форсом | Принудительная перезагрузка во время работы с корзиной = потеря данных | LOW | `skipWaiting` НЕ использовать автоматически; показать «перезапустите приложение для обновления» |

#### Differentiators

| Фича | Ценность | Сложность | Заметки |
|------|----------|-----------|---------|
| Прогресс обновления («Загрузка фото: 23 / 47 новых») | Агент видит что происходит, не думает что зависло | MEDIUM | Счётчик в UI; service worker отправляет `postMessage` с прогрессом |
| Обновление только данных (без перезагрузки страницы) | Не прерывает текущую сессию; новые цены появляются без закрытия приложения | HIGH | Данные в IndexedDB → React state перечитывает из DB после синхронизации; нет hard reload |
| Версионирование данных каталога (timestamp последнего обновления) | Основа для умного diff — есть ли вообще новые данные | MEDIUM | Хранить `catalogVersion` (timestamp или hash) в IndexedDB; при обновлении сравнивать с сервером |

#### Anti-Features

| Фича | Почему хочется | Почему нет | Вместо этого |
|------|---------------|-----------|--------------|
| Автообновление в фоне когда появляется сеть (без промпта) | «Всегда свежие данные» | Агент может работать со старым прайсом намеренно (показ клиенту идёт); внезапная смена цен в момент показа = путаница | Явный промпт: «Есть обновление — обновить сейчас или позже?» |
| Инвалидировать весь кэш фото при каждом обновлении | Простая реализация | Ежедневная перекачка 850 фото ≈ 68 MB; на 4G = 5+ мин, LTE = 1-2 мин; агент злится | Diff по списку URL: только новые `imageUrl`, которых не было в предыдущей версии JSON |

### Зона 4: Сигналы свежести (freshness / staleness)

#### Table Stakes

| Фича | Почему ожидается | Сложность | Зависимости от существующего |
|------|------------------|-----------|------------------------------|
| Метка «Данные за ЧЧ:ММ ДД.ММ» в шапке или рядом с данными | Агент должен знать актуальность прайса перед показом клиенту — это основная бизнес-доверенность | LOW | Записывать `syncTimestamp` в IndexedDB при каждом обновлении; читать при старте |
| Визуальный акцент если данные старше 24 часов | Если агент не обновился с вечера — жёлтый/оранжевый индикатор рядом с меткой времени | LOW | `Date.now() - syncTimestamp > 86400000` → изменить цвет метки |
| При первом запуске без кэша — явный экран «Нет данных» с кнопкой синхронизации | Лучше честный экран, чем пустой список или ошибка | LOW | Офлайн-fallback + проверка наличия данных в IndexedDB |

#### Differentiators

| Фича | Ценность | Сложность | Заметки |
|------|----------|-----------|---------|
| Метка свежести в строке состояния офлайн-режима | Когда агент офлайн, метка «Офлайн • Данные за 08:30 сегодня» даёт уверенность что данные актуальны | LOW | Объединить offline-баннер с timestamp в одну строку |

#### Anti-Features

| Фича | Почему хочется | Почему нет | Вместо этого |
|------|---------------|-----------|--------------|
| Автоматически форсировать обновление если данные старше X часов | «Защита от устаревших данных» | Агент может работать в поле без сети весь день — принудительный блок доступа к каталогу разрушит его работу | Предупреждение (жёлтый цвет), но НЕ блокировка |

### Зона 5: Обратная связь по хранилищу (storage feedback)

#### Table Stakes

| Фича | Почему ожидается | Сложность | Зависимости от существующего |
|------|------------------|-----------|------------------------------|
| Корректная работа при нехватке места (graceful degradation) | Если телефон переполнен и кэш не записался — каталог не должен «падать» молча | MEDIUM | `try/catch` вокруг всех IndexedDB/Cache API операций; показать тост «Не удалось сохранить данные» |
| Сообщение об ошибке при неудачной синхронизации | Агент должен знать что «обновление не завершилось» — не думать что всё ок | LOW | Catch ошибок при sync → тост с текстом ошибки + кнопка «Попробовать снова» |

#### Differentiators

| Фича | Ценность | Сложность | Заметки |
|------|----------|-----------|---------|
| Показывать объём занятого хранилища («Каталог занимает ~45 MB») | Прозрачность; агент понимает почему телефон «тормозит» и может принять решение | LOW | `navigator.storage.estimate()` (поддерживается Safari 17+, Android Chrome); показать в настройках или экране синхронизации |
| Кнопка «Очистить кэш фото» (освободить место) | Если агент жалуется на место — легко освободить без удаления приложения | MEDIUM | Удалить только cache `image-cache` через Cache API; данные (JSON) сохранить |
| Запрос persistent storage при первой синхронизации | Защищает кэш от автоматической очистки браузером при давлении диска | LOW | `navigator.storage.persist()` — сразу после успешной первой синхронизации; на iOS 17+ работает |

#### Anti-Features

| Фича | Почему хочется | Почему нет | Вместо этого |
|------|---------------|-----------|--------------|
| Подробная разбивка «X MB данные, Y MB фото, Z MB скрипты» | Прозрачность | Добавляет сложность UI; `usageDetails` не все браузеры поддерживают полно | Простая цифра «≈ X MB» из `usage` поля `StorageManager.estimate()` |

```
[Установка PWA (manifest + SW)]
    └──требует──> [Service Worker зарегистрирован]
                      └──требует──> [HTTPS (Vercel — уже есть)]

[Офлайн-доступ к товарам]
    └──требует──> [Service Worker зарегистрирован]
    └──требует──> [Данные каталога в IndexedDB]
                      └──заполняется──> [Синхронизация (кнопка «Обновить»)]

[Офлайн-доступ к фото]
    └──требует──> [Cache API через Workbox]
    └──требует──> [Cloudinary-домен добавлен в Workbox runtimeCaching]
                      └──уже есть──> [remotePatterns в next.config.mjs]

[Умный diff фото]
    └──требует──> [Версионирование каталога (syncTimestamp)]
    └──требует──> [Предыдущий список imageUrl сохранён в IndexedDB]

[Баннер «Доступно обновление»]
    └──требует──> [Service Worker lifecycle: updatefound + postMessage]

[Метка свежести данных]
    └──требует──> [syncTimestamp в IndexedDB]

[Запрос persistent storage]
    └──зависит от──> [Первая успешная синхронизация]

[iOS install prompt (инструкция)]
    └──конфликтует──> [Android beforeinstallprompt]
    └──решение──> [Определение платформы: iOS UA → инструкция, Android → нативный промпт]

[Корзина офлайн]
    └──уже работает──> [localStorage в CartProvider — без изменений]

[Отправка заказа (Telegram deep-link)]
    └──требует сети──> [Блокировать кнопку офлайн + пояснение]
```

### Ключевые замечания по зависимостям

- **Офлайн-данные требуют IndexedDB** — это новый слой хранения. Текущий `getProducts()` в `lib/sheets.ts` нужно обернуть: онлайн → fetch + сохранить в IDB; офлайн → читать из IDB.
- **Diff фото зависит от сохранения предыдущего состояния** — при каждой синхронизации нужно сохранять список `imageUrl` для сравнения.
- **Cloudinary URL-ы стабильны** — фото не переименовываются (только новые товары = новые URL). Diff безопасен: если URL тот же → файл не изменился (Cloudinary content-addressed).
- **iOS Safari Home Screen** получает квоту до 60% диска (Safari 17+), но в браузере Cache API ограничен ~50 MB. Стратегия: запрашивать `navigator.storage.persist()` сразу после установки.
- **Корзина (localStorage) не требует изменений** — уже работает офлайн.

## MVP Definition

### Запустить с (v1.3 Launch)

Минимум для полноценной офлайн-работы агента в поле:

- [ ] Service worker + `manifest.json` — приложение устанавливается на домашний экран
- [ ] iOS install prompt (инструкция «Поделиться → Добавить») — иначе iOS-агенты не установят
- [ ] Данные каталога (~900 товаров, структура групп) в IndexedDB — офлайн-листалка работает
- [ ] Кнопка «Обновить каталог» — явный ручной триггер синхронизации онлайн
- [ ] Умный diff фото: качать только новые URL, не все 850 — без этого ежедневная синхронизация невыносима
- [ ] Офлайн-индикатор в шапке + метка «Данные за ЧЧ:ММ» — агент понимает что работает офлайн и знает свежесть данных
- [ ] Graceful degradation: корзина офлайн работает, отправка заказа заблокирована с пояснением

### Добавить после валидации (v1.3.x)

- [ ] Прогресс загрузки фото («Загрузка 23/47») — когда агенты пожалуются что «непонятно зависло»
- [ ] Кнопка «Очистить кэш фото» — когда появятся жалобы на место
- [ ] Показ объёма хранилища — при запросе от агентов
- [ ] Баннер «Есть обновление» от service worker — после того как базовая синхронизация стабильна

### Отложить на v2+ (многоаккаунтность)

- [ ] Фоновая синхронизация (Background Sync API) — нужен аккаунт для идентификации агента
- [ ] Push-уведомления «каталог обновлён» — нужна подписка на уведомления на каждом устройстве
- [ ] Персональный кэш (разные данные для разных агентов) — требует многопользовательской архитектуры (v2.0)

## Критические технические ограничения (влияют на фичи)

| Ограничение | Платформа | Влияние на фичи |
|-------------|-----------|-----------------|
| Cache API ≤50 MB (браузер) | iOS Safari | Нельзя кэшировать все 850 фото сразу; нужна стратегия progressive/on-demand |
| Cache API до 60% диска (Home Screen PWA, iOS 17+) | iOS standalone | Если агент установил как приложение — лимит снимается; запрашивать `persist()` |
| Нет `beforeinstallprompt` | iOS | Ручной промпт с инструкцией обязателен |
| 7-day eviction если PWA не открывалась | iOS (best-effort mode) | Запрашивать persistent storage; данные исчезают за неделю простоя |
| Нет Background Sync надёжного | iOS до 16+ | Явная кнопка «Обновить» вместо фонового автообновления |
| Cloudinary URL стабильны по имени файла | Все | Diff по URL безопасен: тот же URL = тот же файл; нет нужды в ETag |
| ISR revalidate=300 на Vercel | Сервер | При синхронизации нужно запрашивать `/api/products` (force-dynamic endpoint), а не закэшированную HTML-страницу |
