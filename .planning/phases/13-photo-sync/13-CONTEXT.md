## Phase Boundary

Этап доводит до офлайна **фотографии товаров** — последний слой данных, который ещё не работает без сети (товары/цены/навигация уже офлайн после этапов 11–12). Три результата:

1. **IMG-01/IMG-02:** фото товара, открытого ранее при сети, доступно в авиарежиме — в карточке и в полноэкранном просмотрщике с зумом (`components/Lightbox.tsx`).
2. **SYNC-01/SYNC-02:** агент по требованию жмёт «Обновить» → подтягивается свежий каталог И **только новые** фото (diff по списку ссылок), а не все ~900 заново.
3. **IMG-03:** кэш фото имеет жёсткий предел и не переполняет телефон (особенно iPhone — лимит Cache Storage ~50 МБ).

**Требования этапа:** IMG-01, IMG-02, IMG-03, SYNC-01, SYNC-02.

**Вне этого этапа** (см. Deferred Ideas): прогресс-бар синхронизации «Загрузка фото: 23/47» (SYNC-04, v1.3.x); кнопка «Очистить кэш фото» (IMG-04, v1.3.x); показ занятого объёма хранилища (IMG-05, v1.3.x); install prompt (этап 14); кнопка «скачать все 900 фото разом» (явно out-of-scope в REQUIREMENTS.md — риск квоты iOS).

<decisions>
## Implementation Decisions

> Владелец дал явный мандат на этом этапе: «Делай так, как считаешь нужным, как поступил бы профессионал, задавай вопросы, только если необходимо». Решения ниже — выбор владельца из предложенных вариантов + инженерные детали на усмотрение Claude.

### Кнопка «Обновить» (SYNC-01)
- **D-01 (где живёт):** Иконка-обновление (↻) **в синей шапке** каталога, рядом с шестерёнкой настроек / корзиной — всегда на виду. Важная причина: полоска статуса `OfflineBar` по решению этапа 12 (D-01) **скрыта** при «онлайн + данные свежие» — а «Обновить» агент жмёт именно в этом состоянии. Поэтому кнопку нельзя сажать только на полоску — нужно постоянно доступное место. Шапка (`app/catalog/[secret]/layout.tsx`) — серверный компонент; кнопка реализуется как клиентский компонент-«остров» (паттерн уже использован для `OfflineBar`).
- **D-02 (фидбэк при нажатии):** Минимальный честный фидбэк без прогресс-бара (прогресс по фото — SYNC-04, отложен): иконка **крутится** во время обновления → короткая **галочка «готово»** по завершении. После успеха метка свежести в `OfflineBar` обновляется (новый `syncTimestamp`).
- **D-03 (что обновляет):** Одна кнопка обновляет И данные каталога, И фото за одно нажатие (соответствует критерию успеха №2 в ROADMAP.md). Офлайн кнопка неактивна / нет смысла (нет сети — нечего тянуть); поведение блокировки — на усмотрение исполнителя (можно скрыть/задизейблить, как у кнопки отправки заказа в этапе 12).

### Докачка новых фото при «Обновить» (SYNC-02, IMG-01, IMG-03)
- **D-04:** **Гибрид «новые — сразу, первая загрузка — лениво»:**
  - При нажатии «Обновить» — diff текущих `imageUrl` против `meta.prevImageUrls`; **активно prefetch-им только новые** URL (огонь-и-забыл `fetch`, SW перехватит и закэширует). Новинок в день обычно единицы-десятки — трафик копеечный, к вечеру всё под рукой офлайн.
  - При **самой первой синхронизации** (`prevImageUrls` пуст/отсутствует) — НЕ качать все ~900 фото разом (взрыв квоты iOS, долгая первая загрузка, анти-паттерн №1 исследования). Эти фото наполняют кэш **лениво по мере просмотра** (CacheFirst on-demand).
  - После каждой синхронизации — обновить `meta.prevImageUrls` текущим списком ссылок для следующего diff.
- **D-05 (потолок кэша остаётся):** Жёсткий лимит `maxEntries: 450` + `maxAgeSeconds: 7 дней` в `ExpirationPlugin` (уже в каркасе `app/sw.ts`) — не снимать. При переполнении Serwist сам удаляет старые записи (LRU). Это и есть защита IMG-03 (~50 МБ).

### Заглушка незакэшированного фото офлайн (IMG-01)
- **D-06:** Товар, фото которого не успело закэшироваться, в офлайне показывает **ту же иконку-заглушку «нет фото»**, что и товары без фото вообще. Единообразно, агент её уже знает, не тревожно. Никаких особых пометок «фото появится при сети» — лишний визуальный шум и новый паттерн.

### Claude's Discretion
Чисто инженерные решения — планировщик/исполнитель определяют сами:
- **⚠ КЛЮЧЕВОЙ технический вопрос — стыковка `next/image` ↔ SW-кэш (для исследователя):** карточки рендерят фото через `next/image` (`components/ProductCard.tsx`), а Next.js Image Optimizer переписывает адрес на `/_next/image?url=<cloudinary>&w=…&q=…`. SW-matcher в `app/sw.ts` сейчас ловит только прямой `^https://res.cloudinary.com/` — он **НЕ совпадёт** с `/_next/image?...`. Значит фото из карточек в текущем виде в кэш по этому правилу не попадут, а prefetch-диф «огонь-и-забыл» по сырым Cloudinary-URL закэширует ДРУГИЕ записи, чем те, что реально запрашивает браузер. Нужно выбрать один согласованный подход: либо кэшировать `/_next/image` (matcher по pathname + учесть, что разные `w`/`q` = разные URL), либо перейти на `unoptimized`/raw Cloudinary URL для фото каталога, либо `loader`, отдающий прямой Cloudinary-URL. Lightbox (`components/Lightbox.tsx`) использует `getHiResUrl(imageUrl)` — проверить, идёт ли он через optimizer или напрямую (разные URL hi-res vs thumbnail = отдельные записи кэша; учесть в diff/prefetch и в потолке 450). **Это нужно решить ДО планирования** — от него зависит, заработает ли офлайн-фото вообще.
- Где именно в `useCatalogSync` / отдельной утилите делать diff и prefetch (хук уже централизует sync; логично добавить туда либо вынести в `lib/syncPhotos.ts`).
- Точная иконка ↻, анимация вращения, реализация состояния «крутится/готово» (Tailwind, стиль синей шапки `blue-600`).
- Как технически связать кнопку «Обновить» с `useCatalogSync` (экспонировать `refetch()`/`sync()` из хука; сейчас sync приватный — вынести наружу).
- Обработка ошибок prefetch (молча, как офлайн — в духе D-04 этапа 11).

## Existing Code Insights

### Reusable Assets
- `app/sw.ts` — CacheFirst-матчер для Cloudinary + `ExpirationPlugin(maxEntries:450, 7д)` уже на месте. Этап в основном «оживляет» этот каркас: добавить prefetch новых URL + diff, не строить кэш-стратегию заново.
- `lib/useCatalogSync.ts` — функция `sync()` уже делает fetch + save IDB + saveMeta(syncTimestamp). Точка вставки diff/prefetch фото и точка для экспонирования `refetch()` под кнопку «Обновить».
- `lib/catalogDb.ts` — `getMeta<string[]>("prevImageUrls")` / `saveMeta("prevImageUrls", urls)` — API готово, ключ заложен на этапе 11.
- `components/OfflineBar.tsx` — клиентский «остров» под шапкой; образец, как встраивать клиентский компонент в серверный layout. Обновляет метку свежести после sync.
- `components/Lightbox.tsx` — полноэкранный просмотр + зум (IMG-02); использует `getHiResUrl(imageUrl)` — проверить путь URL (optimizer vs raw).
- Иконка-заглушка «нет фото» в `components/ProductCard.tsx` — переиспользовать для D-06.

### Established Patterns
- `app/catalog/[secret]/layout.tsx` — синяя шапка (`bg-blue-600`, sticky, `max-w-screen-2xl`), **серверный** компонент. Кнопка ↻ (D-01) — отдельный **клиентский** компонент-остров рядом с настройками/корзиной.
- Diff безопасен: Cloudinary URL content-addressed по имени файла — один URL = одно фото навсегда; новые товары = новые URL; старые не перекачиваются (ARCHITECTURE.md Pattern 3).
- Ошибки сети трактуются «как офлайн», молча (D-04 этапа 11) — prefetch фото следует тому же духу.

### Integration Points
- ⚠ **Стыковка `next/image` ↔ SW** (см. Claude's Discretion D-05-сосед) — самый важный интеграционный риск этапа; решить до планирования.
- Новое (ориентировочно): утилита/функция diff+prefetch фото (в `useCatalogSync` или `lib/syncPhotos.ts`); клиентский компонент кнопки «Обновить» в шапке; экспонирование `refetch`/`sync` из `useCatalogSync`.
- Точки стыковки: `layout.tsx` (кнопка ↻ в шапку), `useCatalogSync` (вызов diff/prefetch после успешного fetch + ручной refetch), `app/sw.ts` (согласовать matcher с реальными URL фото), `catalogDb` (`prevImageUrls`).

## Specific Ideas

- Кнопка «Обновить» = иконка ↻ в шапке, рядом с шестерёнкой/корзиной; вращение во время → галочка «готово» после.

- Приёмка (критерий успеха №5): обязательная ручная проверка на **реальном iPhone** — просмотреть 5–10 товаров → авиарежим → открыть те же карточки → фото видны. Симулятор не годится. (Отметить: на этапах 11–12 iPhone-приёмка откладывалась на конец вехи — см. STATE.md / коммиты этапа 12.)
