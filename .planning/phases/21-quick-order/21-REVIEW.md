# Этап 21: Отчёт по код-ревью

**Проверено:** 2026-07-01
**Глубина:** standard
**Файлов проверено:** 6
**Статус:** issues_found (найдены замечания)

## Резюме

Проверен новый режим каталога «Быстрый набор» (`quick`), доступный только роли
`sales`. Отдельное внимание — ролевому гейту, SSR-безопасности (клиент не должен
видеть агентский режим и не должно быть рассинхрона гидратации), валидации
localStorage и корректной подстановке единицы товара в снимок заказа.

**Хорошее:**
- Ролевой гейт в `CatalogView` (`effectiveMode`, строка 326-327) и в `SettingsPanel`
  (`visibleViews`, строка 66-69) построен правильно: оба требуют `ready && role === "sales"`.
  До `ready` роль считается `client`, поэтому клиент не видит режим `quick` ни на
  первом кадре, ни при гидратации. Рассинхрона гидратации `QuickOrderRow` нет —
  на сервере и на первом клиентском кадре всегда рендерится `presentation`.
- Fallback единицы в снимке заказа обрабатывает пустую строку от `getUnit` корректно
  (`|| "шт"`), а срезка предлога «за » регистронезависима.
- Кап по остатку не дублируется в `QuickOrderRow` — переиспользуется `AddToCartButton`/`useCart`.

**Ключевые замечания** — ниже. Блокеров нет; 4 предупреждения касаются
консистентности данных снимка, защиты localStorage в глубину и мёртвых веток.

**Что это значит:** этап можно принимать после устранения WR-01 и WR-02 —
они влияют на то, что реально увидит человек в истории заказов и что попадёт
в отправленный текст. WR-03/WR-04 и Info — на ваше усмотрение, это про
аккуратность и защиту от повреждённого localStorage.

## Предупреждения (Warnings)

### WR-01: Единица в снимке заказа рассинхронизирована с текстом заказа и подписью в корзине

**Файл:** `app/catalog/[secret]/cart/page.tsx:218-219`, `146`, `256`

**Проблема:** С этого этапа снимок истории заказа пишет реальную единицу из
`getUnit` («блок», «кг», «коробка» и т.д.). Но при этом:
- Подпись цены в самой корзине жёстко захардкожена как «₽ / шт»
  (строка 146: `{effectivePrice(product, priceForm).toFixed(2)} ₽ / шт`).
- Текст заказа, уходящий в Telegram/MAX, единицу вообще не содержит
  (строка 256/328: `• ${product.name} × ${quantity} = …`).

В итоге для товара с фасовкой «за блок» клиент в корзине видит «₽ / шт»,
владельцу уходит «× N» без единицы, а в истории заказа сохраняется «блок».
Три разных представления одной и той же строки заказа. Для B2B-каталога,
где «шт» и «блок» — это разные объёмы, это риск неверного понимания заказа.

**Fix:** Свести единицу к одному источнику. Либо подставлять реальную единицу
во всех трёх местах (подпись в корзине, текст заказа, снимок), либо, если для
этапа 21 единица нужна только в истории, оставить подпись «/ шт» в корзине
временной и явно синхронизировать текст заказа. Минимально — добавить единицу
в текст заказа:
```ts
const unitLabel = getUnit(product).replace(/^за\s+/i, "") || "шт";
// ...
`• ${product.name} × ${quantity} ${unitLabel} = ${(effectivePrice(product, priceForm) * quantity).toFixed(2)} ₽`
```
и заменить жёсткое «/ шт» на строке 146 на ту же величину.

### WR-02: Дублирование логики единицы — `getUnit(...).replace(/^за\s+/i,"")` в двух местах вместо шва

**Файл:** `app/catalog/[secret]/cart/page.tsx:218-219`; `components/QuickOrderRow.tsx:56`; `lib/getUnit.ts:16`

**Проблема:** Комментарий в `lib/getUnit.ts` объявляет getUnit «единственной точкой
шва» для чтения единицы. Но потребители получают строку с предлогом («за шт»)
и по-разному её обрабатывают: `QuickOrderRow` показывает как есть («за блок»),
а `buildOrderSnapshot` срезает предлог инлайн-регексом. Логика «за X → X» размазана
по вызывающим местам. Когда на этапе 21b в `getUnit` добавится приоритет ручной
правки, любой потребитель, забывший про срезку предлога, получит рассогласование.

**Fix:** Вынести нормализацию в сам шов, например экспортировать
`getUnitBare(product)` (без предлога) рядом с `getUnit`, и в снимке использовать его:
```ts
// lib/getUnit.ts
export function getUnitBare(product: Product): string {
  return getUnit(product).replace(/^за\s+/i, "");
}
```
Тогда `buildOrderSnapshot`: `const unit = getUnitBare(product) || "шт";`

### WR-03: `viewMode="quick"` принимается из localStorage без проверки роли (защита в глубину)

**Файл:** `components/CatalogSettings.tsx:110-112`

**Проблема:** При монтировании `viewMode` восстанавливается из localStorage и
значение `"quick"` принимается безусловно, без сверки с ролью. Рендер защищён
(`effectiveMode` откатит клиента к `presentation`), поэтому это не BLOCKER. Но
состояние `viewMode === "quick"` у клиента всё равно установится. Это опора всего
гейта на единственный производный расчёт `effectiveMode`: любой будущий потребитель
`viewMode` (а не `effectiveMode`) обойдёт защиту. Клиент с подделанным
localStorage (`viewMode=quick`, `userRole=client`) держит «агентское» значение
в состоянии настроек.

**Fix:** При восстановлении `viewMode` из localStorage не принимать `"quick"`,
если сохранённая роль не `sales` — по образцу расчёта дефолта сетки строкой ниже:
```ts
const savedRole = localStorage.getItem("userRole");
if (v === "list" || v === "grid" || v === "presentation") setViewMode(v);
else if (v === "quick" && savedRole === "sales") setViewMode(v);
// иначе — остаётся дефолт "presentation"
```

### WR-04: При роли client с сохранённым `viewMode="quick"` в панели не подсвечен ни один режим

**Файл:** `components/SettingsPanel.tsx:121-131`, `66-69`

**Проблема:** Подсветка активной кнопки вида — `viewMode === v.key` (строка 126).
Если пользователь-агент выбрал «Набор» (`viewMode="quick"`), а затем переключился
на роль «Клиент» (кнопка на строке 87), пункт «Набор» исчезает из `visibleViews`,
но `viewMode` остаётся `"quick"` (и в состоянии, и в localStorage). В результате
в переключателе видов не подсвечен ни один пункт — пользователь видит, что каталог
показан как «Презентация» (через `effectiveMode`), но панель настроек не отражает
ни один активный режим. Визуальное рассогласование «что показано» vs «что выбрано».

**Fix:** При переключении роли на `client` сбрасывать `viewMode` с `"quick"` на
`"presentation"`, либо подсвечивать кнопку по `effectiveMode`-эквиваленту. Проще —
в обработчике `setRole("client")` добавить откат вида:
```ts
onClick={() => { setRole("client"); if (viewMode === "quick") setViewMode("presentation"); }}
```

## Информационные замечания (Info)

### IN-01: Мёртвая ветка «Нет в наличии» в QuickOrderRow

**Файл:** `components/QuickOrderRow.tsx:52`, `89-95`

**Проблема:** `QuickOrderRow` рендерит ветку «Нет в наличии» при `product.stock <= 0`.
Но в `CatalogView` все товары фильтруются по `stock > 1` (`grouped`, строка 222)
и `stock <= 1` (`flatFiltered`, строка 210-211) — товары с нулевым остатком до
`QuickOrderRow` не доходят. Ветки `!inStock` (фон `bg-gray-50 opacity-60` и
«Нет в наличии») в текущем потоке недостижимы. Не вредно, но вводит в заблуждение
при чтении и маскирует, что фильтрацию наличия делает родитель.

**Fix:** Либо оставить как задел под этап 22 (наличие) с комментарием, что ветка
пока недостижима, либо убрать до появления реального сценария.

### IN-02: Рассинхрон границы фильтра остатка между flat и grouped

**Файл:** `components/CatalogView.tsx:210-211`, `222`

**Проблема:** В плоском списке условие `if (p.stock <= 1) return false`
(оставляет `stock > 1`), в групповом — `p.stock > 1`. Границы совпадают, но
записаны по-разному (инверсия), что легко разъезжается при правках. Это не новый
код этапа 21, но режим `quick` теперь рендерится через обе ветки, поэтому важно,
чтобы правило наличия было единым.

**Fix:** Вынести предикат видимости в общую функцию, например
`const isVisible = (p: Product) => p.stock > 1;`, и использовать в обоих `useMemo`.

### IN-03: `MAX_ORDER_URL` типизирован небезопасно (`as string`) при уже выполненной проверке

**Файл:** `app/catalog/[secret]/cart/page.tsx:361`

**Проблема:** `fetch(MAX_ORDER_URL as string, …)` использует `as string`, хотя выше
(строка 318) есть ранний `return null` при `!MAX_ORDER_URL`. Приведение типом
избыточно и скрывает, что сужение уже произошло; при рефакторинге раннего return
`as string` замаскирует потенциальный `undefined`.

**Fix:** Убрать `as string` — после гварда `if (!MAX_BOT || !MAX_ORDER_URL) return null`
TypeScript уже сужает тип. Если сужение не проходит из-за захвата в замыкание,
скопировать в локальную const внутри `handleSend`.
