# Этап 02-1: Отчёт код-ревью

**Проверено:** 2026-06-07
**Глубина:** standard
**Файлов проверено:** 1
**Статус:** issues_found

## Сводка

Проверён единственный изменённый файл `uploader/app.py` — синхронный маршрут `/update`
переделан в асинхронный фоновый поток с журналом истории. Архитектура выбрана грамотно
(неблокирующий `acquire`, освобождение Lock в `finally`, атомарная запись через
`tempfile` + `os.replace`, разделение «оператор видит нейтральный текст / владелец —
детали»). Но при адверсариальной проверке вскрылись три серьёзных дефекта:

1. **Утечка/вечная блокировка замка** — если `Thread.start()` упадёт, `PROCESS_LOCK`
   останется захваченным навсегда, и кнопка «Обновить» больше не сработает до перезапуска
   сервиса. Освобождение в `finally` потока этот случай не покрывает.
2. **XSS в таблице истории** — имена файлов и `result_text` вставляются в DOM через
   `innerHTML` без экранирования. Оператор сам задаёт имена загружаемых файлов.
3. **Гонка вокруг `history.json`** — `load → insert → save` не атомарна как операция;
   при одновременном `append_history` (поток фона) и `update_history` записи могут
   потеряться.

Что это значит: первый дефект может «насмерть» заблокировать загрузчик в проде,
второй — позволяет внедрить скрипт в страницу через имя файла, третий приводит к
исчезновению строк истории. Ниже — конкретика и правки.

## Критические замечания

### CR-01: Падение `Thread.start()` оставляет PROCESS_LOCK захваченным навсегда

**Файл:** `uploader/app.py:461-481`
**Проблема:** Замок захватывается в маршруте `update()` (строка 461), а освобождается
только внутри `_process_async` в блоке `finally` (строка 238). Но если исключение
возникнет МЕЖДУ захватом и успешным стартом потока — например, `append_history()`
(строка 468) бросит исключение при записи `history.json`, либо `threading.Thread(...).start()`
(строка 477) упадёт из-за нехватки ресурсов ОС, — то `_process_async` НИКОГДА не
запустится, его `finally` не выполнится, и `PROCESS_LOCK` останется захваченным
навечно. Все последующие нажатия «Обновить» будут возвращать «Обработка уже идёт»
до перезапуска службы `catalog-uploader.service`. Это полная потеря работоспособности
загрузчика без видимой причины.

**Исправление:** обернуть участок от захвата до старта потока в try/except и освобождать
замок при любой ошибке до того, как ответственность перейдёт к потоку:
```python
if not PROCESS_LOCK.acquire(blocking=False):
    return jsonify(ok=False, message="Обработка уже идёт, подождите.")
try:
    current_files = list_files()
    entry_id = append_history({...})
    thread = threading.Thread(target=_process_async, args=(entry_id,), daemon=True)
    thread.start()
except Exception:
    PROCESS_LOCK.release()   # поток не стартовал — освобождаем сами
    log.exception("Не удалось запустить фоновую обработку")
    return jsonify(ok=False, message="Не удалось запустить обработку, попробуйте ещё раз.")
log.info("Запущен фоновый поток обработки, entry_id=%s", entry_id)
return jsonify(ok=True, message="Файлы отправлены, обработка идёт.")
```

### CR-02: XSS через имена файлов и текст истории (innerHTML без экранирования)

**Файл:** `uploader/app.py:682-689` (рендер), косвенно `662-690`
**Проблема:** В `renderHistory()` строка таблицы собирается через шаблонную строку и
присваивается `container.innerHTML` (строка 689). При этом `filesText`
(`item.files.join(", ")`, строка 680) и `resultText` (`item.result_text`, строка 678)
подставляются БЕЗ HTML-экранирования. Имена файлов задаёт оператор при загрузке.
Хотя `sanitize_filename()` (строка 243-249) вырезает многие символы regex'ом
`[^\w.\-() ]+`, класс `\w` с флагом `re.UNICODE` пропускает массу не-ASCII символов;
важнее то, что любой источник (например, будущее изменение `result_text` со стороны
сервера или содержимое восстановленного `history.json`) может содержать `<`, `>`, `"`.
Файл `history.json` персистентный — если в него попадёт строка с разметкой, она
выполнится в браузере оператора. Это hardcoded-доверие к данным на клиенте.

**Исправление:** экранировать перед вставкой в HTML либо строить DOM через
`textContent`:
```javascript
function esc(s) {
  return String(s).replace(/[&<>"']/g, c => (
    {'&':'&amp;','<':'&lt;','>':'&gt;','"':'&quot;',"'":'&#39;'}[c]));
}
// ...
<td class="fnames">${esc(filesText)}</td>
<td class="result ${statusCls}">${esc(resultText)}</td>
<td class="ts">${esc(fmtTs(item.ts))}</td>
```

### CR-03: Гонка записи `history.json` — потеря записей при конкурентных вызовах

**Файл:** `uploader/app.py:123-144` (`append_history`, `update_history`)
**Проблема:** Каждая функция делает `load_history()` → модификация в памяти →
`_save_history_atomic()`. Сама запись файла атомарна (os.replace), но связка
«прочитал-изменил-записал» — НЕТ. Сценарий: маршрут `/update` в основном потоке Flask
вызывает `append_history` (строка 468), почти одновременно предыдущий фоновый поток
вызывает `update_history` (например, строка 213). Оба прочитали один снимок списка,
оба пишут — побеждает последний, изменения первого теряются (читается обновление
статуса либо новая запись исчезает). PROCESS_LOCK защищает только саму обработку,
но `append_history` в маршруте вызывается ВНЕ зоны, синхронизированной с `update_history`
прошлого потока (новый поток ещё не стартовал/старый ещё пишет финал). Под gunicorn
с `-w 1` риск ниже, но `update()` исполняется в одном из рабочих тредов Flask
параллельно с потоком `_process_async` — оба трогают файл.

**Исправление:** ввести отдельный `threading.Lock` для всех операций с историей и
оборачивать в него весь цикл read-modify-write:
```python
HISTORY_LOCK = threading.Lock()

def append_history(entry: dict) -> str:
    entry_id = secrets.token_hex(8)
    entry["id"] = entry_id
    with HISTORY_LOCK:
        history = load_history()
        history.insert(0, entry)
        _save_history_atomic(history[:10])
    return entry_id

def update_history(entry_id: str, **fields) -> None:
    with HISTORY_LOCK:
        history = load_history()
        for item in history:
            if item.get("id") == entry_id:
                item.update(fields)
                break
        _save_history_atomic(history)
```

## Предупреждения

### WR-01: Проверка секрета уязвима к таймингова атаке

**Файл:** `uploader/app.py:392-394`
**Проблема:** `token != APP_SECRET` — обычное сравнение строк, которое завершается на
первом несовпавшем символе. Теоретически позволяет посимвольно подбирать секрет по
времени ответа. Секрет в URL — единственный механизм доступа ко всему загрузчику
(может запустить обновление/откат каталога), поэтому утечка критична.
**Исправление:** использовать постоянное по времени сравнение:
```python
import hmac
def check(token: str) -> None:
    if not APP_SECRET or not hmac.compare_digest(token, APP_SECRET):
        abort(404)
```

### WR-02: `f.save()` без обработки ошибок при сбое записи на диск

**Файл:** `uploader/app.py:421-423`
**Проблема:** `f.save(str(dest))` (строка 422) может бросить `OSError` (диск переполнен,
нет прав, путь занят). Исключение не перехвачено — маршрут вернёт 500 с трассировкой,
а уже сохранённые файлы из той же партии останутся, частично загруженный файл может
повиснуть. Оператор увидит техническую ошибку Flask вместо нейтрального сообщения,
что противоречит цели этапа (детали — только владельцу).
**Исправление:** обернуть сохранение в try/except, при ошибке добавить файл в `skipped`
и залогировать; не прерывать обработку остальных файлов в партии.

### WR-03: `datetime.utcnow()` устарел и теряет признак UTC

**Файл:** `uploader/app.py:469`
**Проблема:** `datetime.utcnow().isoformat()` возвращает naive-метку без суффикса `Z`/
смещения. На клиенте `fmtTs` (строка 655) компенсирует это дописыванием `"Z"`, но это
хрупкая связка: метка в `history.json` неоднозначна, а `utcnow()` объявлен deprecated в
Python 3.12+ (проект на 3.13 — см. pyc в git status). При любом другом потребителе
истории время будет интерпретировано как локальное.
**Исправление:**
```python
from datetime import datetime, timezone
"ts": datetime.now(timezone.utc).isoformat(),
```

### WR-04: При `warn` файлы уже отправлены в архив до решения владельца

**Файл:** `uploader/app.py:191-209`
**Проблема:** `archive_incoming()` (строка 191) вызывается ДО проверки `warn` (строка 192)
и перемещает файлы из `INCOMING_DIR` в `LAST_BATCH_DIR`, очищая очередь. Если затем
сработал `warn` и владелец захочет повторно прогнать те же файлы — в очереди их уже нет,
они в архиве последней партии, который перетирается при следующей загрузке (строки 360-364).
Логически это потеря исходных данных в спорном сценарии, ради которого ветка `warn`
и существует (отложить решение). Это пограничный дефект корректности, а не только стиль.
**Исправление:** при `warn` не очищать очередь (не вызывать `archive_incoming` для этой
ветки) либо архивировать в отдельную несбрасываемую папку до решения владельца.

### WR-05: Откат и обновление не защищены общим замком — возможен конфликт

**Файл:** `uploader/app.py:495-499` (`rollback`) против `448-481` (`update`)
**Проблема:** Маршрут `/rollback` синхронно вызывает `rollback_catalog()` (мутация Google
Sheet) и НЕ проверяет `PROCESS_LOCK`. Если оператор нажмёт «Откатить» в момент, когда
фоновый `_process_async` находится между `run_upload()` и `rollback_catalog()`/`stash_new()`,
два процесса будут одновременно дёргать `sheet_tool.py` на одной таблице — состояние
каталога станет непредсказуемым (бэкап/откат/перезапись пересекутся).
**Исправление:** в `rollback()` тоже захватывать `PROCESS_LOCK` (с неблокирующим acquire
и освобождением в finally) или возвращать «Идёт обработка, дождитесь завершения», если
замок занят.

## Информационные замечания

### IN-01: `_save_history_atomic` на Windows не вполне атомарен при открытом файле

**Файл:** `uploader/app.py:113`
**Проблема:** `os.replace` на Windows бросит `PermissionError`, если целевой
`history.json` открыт другим процессом (антивирус, бэкап-агент). Деплой указан на
daniella (вероятно Linux), но проект разрабатывается на Windows 11. Стоит залогировать
исключение записи истории, а не дать ему всплыть в неожиданном месте.
**Исправление:** обернуть вызовы записи истории в try/except с логированием, чтобы сбой
журнала не валил обработку.

### IN-02: Magic numbers без констант

**Файл:** `uploader/app.py:132` (`[:10]`), `715` (`4000`), `128` (`token_hex(8)`)
**Проблема:** лимит истории `10`, интервал поллинга `4000` мс, длина id зашиты числами
в нескольких местах (на сервере и на клиенте). При изменении легко рассинхронизировать.
**Исправление:** вынести `HISTORY_LIMIT = 10` в константу модуля; интервал поллинга —
в JS-константу.

### IN-03: Поллинг истории не имеет ограничения по времени

**Файл:** `uploader/app.py:707-716`
**Проблема:** `startPolling` крутит `setInterval` каждые 4 с, пока в истории есть запись
`processing`. Если фоновый поток завис и НЕ обновил статус (например, `_process_async`
убит OOM-киллером до `finally` — хотя finally обычно отрабатывает), запись `processing`
останется навсегда, и страница будет опрашивать сервер бесконечно. Стоит ограничить
число итераций или показывать «слишком долго — обратитесь к администратору».
**Исправление:** счётчик итераций (например, max 150 = 10 минут) с остановкой и
сообщением.

### IN-04: `request.json` без `silent=True` бросит 400 на не-JSON теле

**Файл:** `uploader/app.py:431`
**Проблема:** `(request.json or {})` — при теле без заголовка `Content-Type: application/json`
или с битым JSON `request.json` бросает `BadRequest` (400), а не возвращает None, поэтому
`or {}` не спасает. Клиент шлёт корректный JSON, но при ручном/повторном запросе это
даст необработанную ошибку.
**Исправление:** `(request.get_json(silent=True) or {})`.
