## Резюме

Что проверял: индикатор офлайна (`OfflineBar`), хук состояния сети (`useOnlineStatus`),
форматирование метки свежести (`formatSyncTime`), блокировку отправки заказа в офлайне
(локальная кнопка в `cart/page.tsx` и FAB-кнопка `TelegramButton`), а также интеграцию
полоски в layout каталога.

Общая оценка: код аккуратный, с хорошими комментариями, SSR-безопасный по части `navigator`.
Критических проблем (утечки данных, инъекции, падения) не найдено. Но есть **четыре
функциональных дефекта уровня WARNING**, из-за которых поведение в реальном использовании
отклоняется от заявленного в комментариях/решениях D-01…D-05.

Самое важное — два момента:
1. Полоска `OfflineBar` **не обновляется со временем**: метка «данные за …» и переход в
   жёлтое состояние «старше 24 ч» вычисляются один раз и не пересчитываются. Агент может
   часами видеть «данные за 08:30», когда на деле они уже устарели.
2. Метка свежести **не обновляется после фоновой синхронизации** — `syncedAt` читается из IDB
   ровно один раз при монтировании.

## Предупреждения (Warnings)

### WR-01: OfflineBar не пересчитывает «устаревшесть» со временем

**Файл:** `components/OfflineBar.tsx:46-47`
**Проблема:** `isStale` вычисляется через `Date.now() - syncedAt` прямо в теле компонента.
React НЕ перерисовывает компонент по таймеру — пересчёт случится только при смене состояния
(событие online/offline или новое чтение IDB). Сценарий: агент открыл каталог утром (данные
свежие, полоска скрыта), оставил вкладку открытой. Через сутки данные формально устарели, но
жёлтая предупреждающая полоска (состояние 3 по D-01) **не появится** до перезагрузки или
смены сети. Это прямо ломает заявленное поведение «данные старше 24 ч → жёлтая полоска».
**Исправление:** добавить периодический «тик», чтобы компонент перевычислялся (раз в минуту
достаточно):
```tsx
const [, setTick] = useState(0);
useEffect(() => {
  const id = setInterval(() => setTick((t) => t + 1), 60_000);
  return () => clearInterval(id);
}, []);
```

### WR-02: Метка свежести не обновляется после фоновой синхронизации

**Файл:** `components/OfflineBar.tsx:26-42`
**Проблема:** `syncedAt` читается из IndexedDB один раз в `useEffect([])` при монтировании.
Если фоновая синхронизация (`useCatalogSync`) обновит `syncTimestamp` уже после рендера
полоски, `OfflineBar` об этом не узнает — будет показывать старую метку «данные за …»,
пока пользователь не перезагрузит страницу. Для индикатора свежести это смысловая ошибка:
он показывает не текущую свежесть.
**Исправление:** перечитывать `syncTimestamp` периодически (можно совместить с тиком из WR-01),
либо подписаться на событие завершения синхронизации, если такое есть в слое sync. Минимально:
```tsx
useEffect(() => {
  const reload = async () => {
    try {
      const ts = await getMeta<number>("syncTimestamp");
      if (ts !== undefined) setSyncedAt(ts);
    } catch {}
  };
  void reload();
  const id = setInterval(reload, 60_000);
  return () => clearInterval(id);
}, []);
```

### WR-03: FAB-кнопка TelegramButton — двойное открытие Telegram (web + app)

**Файл:** `components/TelegramButton.tsx:27-37`
**Проблема:** `handleClick` всегда выполняет `window.location.href = appUrl`, а затем через
`setTimeout(1500)` **безусловно** делает `window.open(webUrl)`. Если приложение Telegram
установлено, навигация по `tg://` НЕ отменяет таймер — спустя 1.5 сек откроется ещё и
веб-вкладка `t.me`. На десктопе/в части браузеров пользователь получит лишнюю вкладку поверх
уже открытого приложения. Кроме того, на iOS Safari переход по неизвестной схеме `tg://`
может показать диалог ошибки, если приложения нет, а `setTimeout` всё равно сработает.
**Исправление:** отменять fallback, если страница потеряла фокус/видимость (признак того, что
приложение перехватило переход):
```tsx
const timer = setTimeout(() => window.open(webUrl, "_blank"), 1500);
const onHide = () => { if (document.hidden) clearTimeout(timer); };
document.addEventListener("visibilitychange", onHide, { once: true });
```

### WR-04: Дубль имени `TelegramButton` — два разных компонента

**Файл:** `app/catalog/[secret]/cart/page.tsx:133, 140-182` и `components/TelegramButton.tsx:8`
**Проблема:** в `cart/page.tsx` объявлена локальная функция `TelegramButton` (кнопка
«Отправить заказ в Telegram»), а в `components/TelegramButton.tsx` — глобальная FAB-кнопка
бота с тем же именем. Оба рендерятся на странице корзины: FAB приходит из `layout.tsx:51`,
локальная — из строки 133. Это разные компоненты с одинаковым именем и разной логикой
(`disabled` поведение, текст подсказки, разный username: `ZhukOleh` против `NEXT_PUBLIC_BOT_USERNAME`).
Высокий риск ошибки при сопровождении: правка «не того» TelegramButton. Также на странице
корзины в офлайне у пользователя **две** приглушённые синие кнопки Telegram рядом — визуальная
путаница.
**Исправление:** переименовать локальную функцию в `SendOrderButton` (она отправляет заказ, а
не открывает помощника). Это снимет и смысловой конфликт, и риск правки не того компонента.

## Информация (Info)

### IN-01: Жёстко зашитый username Telegram

**Файл:** `app/catalog/[secret]/cart/page.tsx:6`
**Проблема:** `const TELEGRAM_USERNAME = "ZhukOleh";` зашит в код, тогда как FAB-кнопка берёт
username из `process.env.NEXT_PUBLIC_BOT_USERNAME`. Несогласованный подход: смена адресата
заказов потребует правки исходника и пересборки.
**Исправление:** вынести в переменную окружения (напр. `NEXT_PUBLIC_ORDER_TG_USERNAME`),
как уже сделано для бота.

### IN-02: Нажатие «−» на количестве 1 удаляет товар без подтверждения

**Файл:** `app/catalog/[secret]/cart/page.tsx:92` (вызов `updateQuantity(product.id, quantity - 1)`)
**Проблема:** при `quantity === 1` минус передаёт `0`, и `updateQuantity` (см. `lib/useCart.ts:78`)
удаляет позицию из корзины. Кнопка «−» не дизейблится на единице, в отличие от «+», который
дизейблится по остатку. Для отдельной позиции это, возможно, ОК, но «Очистить ВСЮ корзину»
требует confirm, а тихое удаление позиции — нет. Несогласованный UX.
**Исправление:** либо дизейблить «−» при `quantity <= 1` (тогда удаление только через «Удалить»),
либо оставить как есть осознанно. На решение владельца.

### IN-03: `formatSyncTime` не обрабатывает будущие/невалидные timestamp

**Файл:** `lib/formatSyncTime.ts:65-88`
**Проблема:** функция доверяет `syncedAt`. Если в IDB попадёт повреждённое значение (NaN,
отрицательное, дата в будущем из-за неверных часов устройства), `new Date(NaN)` даст метку
вида «данные за NaN:NaN». Не критично (источник — собственный sync), но граница не защищена.
**Исправление:** ранний возврат при `!Number.isFinite(syncedAt)` → «данные не загружены».

### IN-04: Порог 24 ч задан и числом, и текстом — риск рассинхрона

**Файл:** `components/OfflineBar.tsx:18` и комментарии `:6, :44`
**Проблема:** `STALE_THRESHOLD_MS = 24 * 60 * 60 * 1000` живёт только в `OfflineBar`, а
`formatSyncTime` отдельно решает «сегодня/вчера/раньше» по календарным суткам. Граница «вчера»
(календарный день) и граница «устарело» (скользящие 24 ч) — разные шкалы. Например, синхронизация
вчера в 23:00: в 10:00 сегодня данные «вчерашние» по тексту, но younger 24 ч → серая, не жёлтая.
Поведение, возможно, задумано, но стоит зафиксировать в комментарии, что шкалы намеренно разные.
**Исправление:** оставить как есть, но добавить пояснение, чтобы при сопровождении не «починили»
ошибочно.

### IN-05: `useOnlineStatus` доверяет `navigator.onLine` (известно ложноположительный)

**Файл:** `lib/useOnlineStatus.ts:24, 28`
**Проблема:** `navigator.onLine === true` означает лишь наличие сетевого интерфейса, а не реальный
доступ в интернет (Wi-Fi без шлюза, captive portal). Кнопка отправки заказа разблокируется
(`disabled={!isOnline}`), пользователь жмёт — `t.me` не открывается / открывается ошибка. Для
B2B-агента в разъездах это реальный сценарий. Не баг кода, а ограничение API; помечаю как риск.
**Исправление:** на v1 достаточно текущего; в будущем — лёгкий ping/реальная проверка перед
разблокировкой критичных действий. Не блокер для этого этапа.
