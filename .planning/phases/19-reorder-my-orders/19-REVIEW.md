## Warnings

### WR-01: `classifyReorder` доверяет `priceAtOrder` как числу — на повреждённой истории получится NaN и падение `.toFixed()`

**Файл:** `lib/reorder.ts:97`, `lib/reorder.ts:132`; проявляется в `app/catalog/[secret]/orders/page.tsx:412`
**Проблема:** В `reorder.ts` строка `const oldPrice = historyItem.priceAtOrder;` принимает значение как
готовое число. Дальше оно идёт в `roundPrice(oldPrice)` (умножение `price * 100`) и в UI — `line.oldPrice.toFixed(2)`.
Но сам же экран истории НЕ доверяет этому полю: в `page.tsx:191` и `page.tsx:257` стоят защиты
`typeof item.priceAtOrder === 'number'`. То есть авторы знают, что `priceAtOrder` может быть `undefined`/строкой
в старых или повреждённых записях localStorage. В пути «Повторить» этой защиты нет:
- `roundPrice(undefined)` → `NaN`, сравнение `NaN !== roundPrice(currentPrice)` всегда `true` → товар без
  изменения цены ошибочно классифицируется как `price_changed`;
- `line.oldPrice.toFixed(2)` при `oldPrice === undefined` → `TypeError: Cannot read properties of undefined`
  → падение модалки сводки.
**Fix:** Нормализовать цену на входе в классификацию:
```ts
const oldPrice = typeof historyItem.priceAtOrder === 'number' && Number.isFinite(historyItem.priceAtOrder)
  ? historyItem.priceAtOrder
  : 0;
```
И/или в модалке защитить вывод: `{(line.oldPrice ?? 0).toFixed(2)}`. Поскольку остальной экран уже
обороняется от не-числа, согласованность здесь обязательна.

### WR-02: Сопоставление по имени теряет дубликаты — `Map` молча перезаписывает товары с одинаковым названием

**Файл:** `lib/reorder.ts:90-92`
**Проблема:** Фолбэк-индекс строится так:
```ts
const catalogByName = new Map<string, Product>(catalog.map((p) => [normalizeName(p.name), p]));
```
Если в каталоге два товара с одинаковым нормализованным именем (разные поставщики/фасовки, например
«Сахар» от Ефимовой и от Пелих), в `Map` останется только ПОСЛЕДНИЙ — предыдущие перезаписываются молча.
Когда позиция из истории не нашлась по `id` (товар переехал, сменился id при перезаливке прайса), фолбэк
по имени может подставить НЕ тот товар: чужого поставщика, с другой ценой/остатком. Клиент думает, что
повторяет свой заказ, а в корзину падает другой SKU. Это именно та хрупкость name-based matching, на
которую просили обратить внимание.
**Fix:** Как минимум — сделать фолбэк по имени консервативным: использовать его только когда совпадение
единственное. Построить `Map<string, Product[]>` и матчить лишь при `arr.length === 1`; при коллизии —
исход `unavailable` (честнее, чем подставить случайный товар):
```ts
const byName = new Map<string, Product[]>();
for (const p of catalog) {
  const k = normalizeName(p.name);
  (byName.get(k) ?? byName.set(k, []).get(k)!).push(p);
}
// ...
if (!matched) {
  const arr = byName.get(normalizeName(historyItem.name));
  if (arr && arr.length === 1) matched = arr[0];
}
```

### WR-03: `SettingsPanel` игнорирует флаг `ready` из `useRole` — переключатель роли мигает «Клиент» до гидратации и допускает запись до загрузки

**Файл:** `components/SettingsPanel.tsx:37`, `components/SettingsPanel.tsx:74-90`
**Проблема:** `useRole()` специально возвращает SSR-safe флаг `ready` (false до монтирования, true после
чтения localStorage), и его контракт прямо требует: «потребители, у которых роль меняет вёрстку, должны
ждать ready=true (D-04)» (`lib/useRole.tsx:19-21,61`). Здесь панель деструктурирует только `{ role, setRole }`
и `ready` не использует. Последствия:
1. До завершения mount-`useEffect` в `RoleProvider` `role` всегда `'client'` — при сохранённой роли
   `'sales'` пользователь на первом кадре видит подсвеченной кнопку «Клиент», затем перещёлк на «Агент»
   (визуальный флик). Панель открывается тапом по шестерёнке, так что чаще всего mount уже прошёл — но
   гарантии нет, и контракт хука нарушен сознательно.
2. `setRole` пишет в localStorage немедленно (`useRole.tsx:48-51`). Если пользователь успеет нажать роль
   ДО того, как отработает читающий `useEffect`, его выбор может быть перезатёрт прочитанным сохранённым
   значением (гонка «запись до чтения»).
**Fix:** Учесть `ready`: либо не рендерить блок роли / показывать его в нейтральном (disabled) состоянии,
пока `!ready`, либо хотя бы не подсвечивать активную кнопку до `ready`:
```ts
const { role, setRole, ready } = useRole();
// ...
className={`... ${ready && role === "client" ? "bg-blue-500 text-white" : "bg-white text-gray-500"}`}
```

### WR-04: Тихая потеря количества при повторе крупного заказа — товар капается по остатку без сигнала пользователю

**Файл:** `lib/useCart.ts:104`, `lib/useCart.ts:112`; вызов из `app/catalog/[secret]/orders/page.tsx:44`
**Проблема:** `addToCartWithQuantity` капает количество по текущему остатку:
`Math.min(existing.quantity + quantity, product.stock)` и `Math.min(quantity, product.stock)`. Это разумная
защита. Но при повторе заказа `classifyReorder` относит товар к `added`/`price_changed` (и считает его в
`addedCount`) на основании только `stock > 1`, не сравнивая запрошенное количество с остатком. Сценарий:
в прошлом заказе было 50 шт, сейчас на остатке 3 — позиция попадает в «Добавлено N товаров», но в корзину
ляжет 3, а не 50. Модалка сводки (`page.tsx:353-361`) рапортует «Добавлено … в корзину» и НЕ упоминает,
что количество урезано. Клиент уверен, что повторил заказ как был, а по факту получил усечённый объём —
молчаливое расхождение ожидания и реальности.
**Fix:** Либо `classifyReorder` должен возвращать «capped»-исход/флаг, когда `historyItem.quantity > stock`,
и модалка должна это показывать («добавлено 3 из 50 — ограничено остатком»). Либо хотя бы пометить такие
строки в `notableLines` сводки. Решение продуктовое — но текущее «молча урезали» стоит исправить.
