## Предупреждения (Warnings)

### WR-01: Товар с ручной правкой группы всё равно получает бейдж «новинка»

**Файл:** `scripts/upload.py:776-801`
**Проблема:** В блоке нового формата (строки 784-792) товар, которого ещё нет в
каталоге, попадает в `new_names` И в группу «Новинки». Далее `apply_edit_memory`
(строка 797) корректно перебивает группу на ту, что владелец указал во вкладке
«Правки» (тип `group`). Но множество `new_names` при этом НЕ очищается — товар в нём
остаётся. В `products_to_rows` бейдж назначается так:
`badge = "новинка" if p["name"] in new_names else ...` (строка 584).

В результате товар, который владелец вручную переместил в реальную группу (то есть
явно «опознал» как уже знакомый), всё равно выйдет в каталог с бейджем «новинка».
Это прямое противоречие сути памяти правок: ручная правка должна означать, что товар
больше не считается новым.

**Как исправить:** после применения правки группы убирать товар из `new_names`.
Например, вернуть из `apply_edit_memory` затронутые ключи или передать `new_names`
внутрь и делать `new_names.discard(p["name"])` при наличии правки `group`:

```python
def apply_edit_memory(products, edit_memory, new_names=None):
    new_names = new_names if new_names is not None else set()
    new_for_memory = 0
    for p in products:
        edit = edit_memory.get(normalize_name(p["name"]))
        if edit:
            if "group" in edit:
                p["display_group"] = edit["group"]
                new_names.discard(p["name"])  # больше не «новинка»
            ...
```

### WR-02: Несогласованность ключа в migrate_overrides — сопоставление по сырому имени, ключ по нормализованному

**Файл:** `scripts/migrate_overrides.py:70-89`
**Проблема:** В `expand_overrides` совпадение правила ищется по
`name_lower = raw_name.lower()` (строки 71, 76, 83), а ключ результата строится через
`normalize_name(raw_name)` (строка 88). Функция `normalize_name` дополнительно
прогоняет имя через `clean_new_name`, который срезает хвостовую единицу
(`, шт` / `, кг` и т.п.). Из-за этого записанный во вкладку ключ может отличаться от
строки, по которой реально сработало правило.

Это создаёт рассинхрон с `apply_edit_memory` в `upload.py`: там товар ищется по
`normalize_name(p["name"])`, где `p["name"]` для нового формата уже очищен
`clean_new_name`, а для старого — НЕТ (в `parse_excel_file` имя берётся как есть, без
`clean_new_name`). Если правило сработало по товару старого формата с хвостовой
единицей в названии, ключ в памяти окажется обрезанным, а ключ при наложении — нет,
и правка не найдётся.

**Как исправить:** сопоставлять и строить ключ из одной и той же нормализованной
формы. Например, искать совпадение по `normalize_name(raw_name)`, а не по
`raw_name.lower()`, чтобы ключ записи и ключ поиска при наложении гарантированно
совпадали:

```python
norm = normalize_name(raw_name)
for prefix, group in PRODUCT_OVERRIDES.items():
    if norm.startswith(normalize_name(prefix)):
        ...
```

(Примечание: утилита разовая и сейчас неработоспособна после удаления словарей —
поэтому это предупреждение, а не блокер. Но та же логика нормализации лежит в основе
рабочего `apply_edit_memory`, см. WR-04.)

### WR-03: SystemExit с кортежем-аргументом не задаёт код выхода и печатает «грязное» сообщение

**Файл:** `scripts/migrate_overrides.py:116, 129, 131`
**Проблема:** `raise SystemExit(1, "сообщение")` кладёт в `SystemExit.code` кортеж
`(1, "сообщение")`, а не целое число. При выходе из программы Python печатает в stderr
весь кортеж целиком (`(1, 'ERROR: ...')`), а код возврата процесса будет 1 не потому,
что вы его задали, а потому что `.code` не является int (любой не-int трактуется как 1).
Проверено: `SystemExit(1, "msg").code == (1, "msg")`. Сообщение выводится в неаккуратном
виде, а намерение «код 1 + понятный текст» не выполняется как задумано.

**Как исправить:** логировать текст и выходить с числовым кодом отдельно:

```python
log.error("credentials.json не найден (GOOGLE_CREDENTIALS_PATH не задан)")
raise SystemExit(1)
```

### WR-04: Расхождение нормализации имени между старым и новым форматом ломает поиск правок

**Файл:** `scripts/upload.py:166-172` (старый формат) vs `242-248` (новый формат), `444`
**Проблема:** В `parse_excel_file` (старый формат) поле `name` сохраняется БЕЗ
`clean_new_name` — с возможной хвостовой единицей (`Соус, шт`). В `parse_new_format`
(новый формат) имя проходит через `clean_new_name` (строка 243). При этом ключ памяти
правок и в `load_edit_memory` (строка 395), и при наложении в `apply_edit_memory`
(строка 444) считается через `normalize_name`, который ВНУТРИ снова вызывает
`clean_new_name`.

Само по себе двойное обрезание не ломает совпадение (нормализация идёт с обеих сторон).
Но риск в том, что владелец во вкладке «Правки» пишет имя товара так, как видит его в
каталоге, а в каталог попадает строка `p["name"]` БЕЗ нормализации (см.
`products_to_rows`, строка 588 — пишется сырой `p["name"]`). То есть отображаемое имя и
ключ сопоставления — разные строки. Владельцу неочевидно, какую именно форму вводить во
вкладку, и при наличии хвостовой единицы/двойных пробелов правка молча не применится
(никакого предупреждения «правка не нашла товар» нет).

**Как исправить:** (1) добавить в `apply_edit_memory` подсчёт/лог правок из памяти,
которые НЕ совпали ни с одним товаром, чтобы такие промахи были видны:

```python
matched_keys = set()
for p in products:
    key = normalize_name(p["name"])
    if key in edit_memory:
        matched_keys.add(key)
        ...
orphan = set(edit_memory) - matched_keys
if orphan:
    log.warning("Правок в памяти без совпадения с товаром: %d", len(orphan))
```

(2) В документации вкладки «Правки» зафиксировать, что в колонку «Товар» пишется
нормализованная форма (нижний регистр, без хвостовой единицы).

## Информационные замечания (Info)

### IN-01: Дублирование загрузки credentials/окружения в трёх функциях

**Файл:** `scripts/upload.py:265-285` (`load_current_groups`), `326-355`
(`load_edit_memory`); `scripts/migrate_overrides.py:110-138`, `304-338`
**Проблема:** Блок «найти credentials.json → собрать scopes → авторизоваться → открыть
таблицу» скопирован почти дословно в четырёх местах. При изменении логики поиска ключа
(например, новый путь) придётся править во всех. Это повышает риск рассинхрона.
**Как исправить:** вынести общий хелпер `_open_spreadsheet()` в `upload.py` и
переиспользовать его из `load_current_groups`, `load_edit_memory` и
`migrate_overrides.py` (последний уже делает это локально в `open_spreadsheet`).

### IN-02: Двойной вызов load_env() в migrate_overrides

**Файл:** `scripts/migrate_overrides.py:221, 309`
**Проблема:** `load_env()` вызывается в `main()` (строка 221) и повторно внутри
`_load_raw_product_names()` (строка 309). Благодаря `os.environ.setdefault` второй вызов
безвреден, но это мёртвое повторное действие, сбивающее с толку при чтении.
**Как исправить:** убрать `load_env()` из `_load_raw_product_names` — окружение уже
загружено в `main()`.

### IN-03: Логически недостижимая ветка `unattributed` помечена как «логическая ошибка»

**Файл:** `scripts/migrate_overrides.py:378-379, 395-396`
**Проблема:** В `_print_dry_run_report` атрибуция раскрытых правок повторно ищется по
`norm_name.startswith(prefix.lower())` и `sub.lower() in norm_name`. Но `norm_name` —
это уже нормализованное имя (с обрезанной хвостовой единицей), тогда как первичное
сопоставление в `expand_overrides` шло по `raw_name.lower()`. Из-за этого расхождения
(см. WR-02) товар, реально попавший под substring-правило по хвостовой единице, может не
атрибутироваться обратно и попасть в `unattributed`, которое логируется как «логическая
ошибка» — хотя ошибки нет, есть рассинхрон форм имени. Ложная тревога в отчёте.
**Как исправить:** атрибутировать по той же форме имени, что использовалась при
раскрытии, либо возвращать из `expand_overrides` пару (исходное правило → ключ) и не
вычислять атрибуцию заново.

### IN-04: «Тихая» потеря правки при двух строках одного типа на один товар

**Файл:** `scripts/upload.py:396-398`
**Проблема:** Если во вкладке «Правки» окажутся две строки для одного товара с
одинаковым типом (например, две `group`), вторая молча перезатрёт первую
(`mapping[key][raw_type] = raw_value`) без предупреждения. Для владельца, который
случайно завёл дубль, это неочевидно — применится «последняя по порядку строк».
**Как исправить:** при перезаписи существующего ключа того же типа выводить
`log.warning` о конфликте, чтобы дубли были заметны.
