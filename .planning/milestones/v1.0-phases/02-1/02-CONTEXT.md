## Граница этапа

Этап переделывает поток страницы загрузчика `uploader/app.py` (Flask на сервере daniella):
синхронный сценарий «нажал «Обновить» → браузер ждёт несколько минут → видит весь результат»
заменяется на асинхронный «нажал → мгновенно «файлы отправлены» → обработка в фоне → подробный
итог только владельцу в Telegram». На странице появляется короткая таблица истории загрузок.

**В границах этапа:**
- `uploader/app.py` — разрыв синхронного `/update` на мгновенный ответ + фоновый поток
- Журнал истории загрузок (персистентный файл на сервере) + endpoint и таблица на странице
- Защита от двойного запуска обработки
- Нейтрализация того, что видит оператор (без подробностей — детали уходят владельцу)
- Деплой переделанного загрузчика на daniella (через субагента sysadmin)

**Вне границ (НЕ трогаем):**
- `scripts/upload.py` — парсер прайсов (Этап 1 завершён и подтверждён)
- Подушка безопасности `scripts/sheet_tool.py` (бэкап/откат) — уже работает
- Telegram-уведомления владельцу `scripts/notify_tg.py` + admin_bot — уже работают
- Память правок (Этап 3), админ-панель (Этап 4)
</domain>

<decisions>
## Решения этапа (зафиксированы)

### Асинхронная обработка (UPL-01, UPL-02)
- **D-01**: endpoint `/<token>/update` после базовой проверки (есть файлы, обработка не идёт)
  немедленно возвращает оператору нейтральное «файлы отправлены» и запускает всю обработку
  (бэкап → `upload.py` → проверка «мало товаров» → уведомление владельцу → запись в историю)
  в фоновом потоке (`threading.Thread`, daemon) внутри того же gunicorn-воркера. Браузер не ждёт.
- **D-02**: защита от двойного запуска — глобальный `threading.Lock` / флаг «идёт обработка».
  Если обработка уже идёт, повторное «Обновить» НЕ запускает второй поток и возвращает
  нейтральное «обработка уже идёт, подождите». (gunicorn `-w 1` — один процесс, `Lock` корректен.)

### Итог только владельцу (UPL-03)
- **D-03**: подробный итог (успех / ошибка разбора / «подозрительно мало товаров» + inline-кнопки)
  отправляется ТОЛЬКО владельцу в Telegram через существующую функцию `notify(...)`. Логика
  warn/rollback/stash_new сохраняется как сейчас — но выполняется в фоне, не на глазах оператора.
- **D-07**: оператор видит только нейтральные статусы («N товаров» / «ошибка» / «мало товаров»),
  без трассировок, тэйлов логов и технических деталей. Все детали — у владельца в Telegram.

### История загрузок (UPL-04)
- **D-04**: история хранится персистентно в JSON-файле на сервере (например `uploader/history.json`,
  путь через env с дефолтом). Запись добавляется при старте обработки и обновляется по завершении.
  Хранить последние 10 записей. Поля записи: время старта (дата/время), статус
  (`processing` / `ok` / `warn` / `error`), число товаров или нейтральный текст итога, имена файлов партии.
- **D-05**: новый endpoint `/<token>/history` отдаёт последние записи JSON-ом; страница рисует
  компактную таблицу (время · файлы · итог). Сразу после «Обновить» в истории появляется строка
  «обрабатывается…»; страница опрашивает `/history` (поллинг ~3–5 c, пока есть строка «обрабатывается»),
  и строка превращается в финальный нейтральный итог — оператор видит, что запуск принят (решение по Q2).

### Откат (Q3)
- **D-06**: кнопку «Откатить к прошлой версии» оставляем оператору на странице без изменений
  (запасной путь). Владелец дополнительно может откатить через Telegram-кнопки.

### Claude's Discretion (детали реализации на усмотрение исполнителя)
- Точный формат и имя файла истории, способ атомарной записи (temp + os.replace).
- Восстановление «зависших» записей `processing` после перезапуска gunicorn во время обработки
  (подушка безопасности и так защищает каталог) — допустимо пометить записи старше таймаута как
  «прервано»; не обязательно для MVP.
- Интервал и условие остановки поллинга истории на странице.
- Вёрстка таблицы истории (в стиле существующей одностраничной HTML/CSS внутри `app.py`).
</decisions>

- Деплой и проверка на сервере — через субагента `sysadmin`; владелец наблюдает (autonomous: false на серверном плане).
