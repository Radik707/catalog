# Phase 16: Локальная история заказов - Context

**Gathered:** 2026-06-27
**Status:** Ready for planning

<domain>
## Phase Boundary

Этап вводит **локальную историю отправленных заказов** на устройстве. При нажатии кнопки
отправки заказа (Telegram или MAX) каталог сохраняет снимок заказа в `localStorage` —
позиции, количества, цены на момент заказа, итоговую сумму, дату-время и канал. Историю
видно на отдельной странице, её можно очистить. Это **фундамент** под «Мои заказы» и
«Повторить заказ» вехи v1.5 — но сами эти функции в этап **не** входят.

**В рамках этапа:**
- Хранилище истории: новый хук-контекст в стиле `useCart`/`useFavorites` (localStorage,
  load-on-mount, тихий try/catch). Согласован с офлайн-моделью v1.3 (HIST-02).
- Запись заказа в историю в момент отправки — встройка в обе кнопки в `cart/page.tsx`.
- Новая страница `/catalog/[secret]/orders` — список «Отправленные заказы».
- Очистка истории (всё + по одной), потолок числа записей, мягкая деградация битых записей.

**Вне рамок этапа (явно):**
- **«Повторить заказ»** (повторное добавление позиций в корзину) — веха v1.5. Сейчас только
  закладываем `id` товара в снимок, чтобы это стало возможным позже.
- **«Мои заказы» как полноценный экран с вкладками/навигацией** — веха v1.5. Сейчас простая
  отдельная страница-список.
- **Серверная история заказов / привязка к 1С / статусы приёмки** — веха v2.0. История на
  этом этапе — чисто локальная и это «что я отправил», а НЕ статус у поставщика (HIST-03).

</domain>

<decisions>
## Implementation Decisions

### Момент записи (HIST-01)
- **D-01:** Заказ записывается в историю **в момент нажатия кнопки отправки** — одинаково
  для обоих каналов (Telegram и MAX). Причина: это единственный надёжный общий сигнал.
  Telegram после `window.open(t.me/...)` нам ничего не сообщает (нажал ли клиент «отправить»
  в мессенджере — неизвестно), у MAX есть ответ сервера, но это тоже не гарантия. Запись
  по клику честно соответствует HIST-03 — «что я отправил со своей стороны».
- **D-02:** **Канал** записи определяется нажатой кнопкой: `telegram` или `max`.
- **D-03:** Корзина после отправки **не очищается** (сохраняем текущее поведение
  `cart/page.tsx` — `clearCart` при отправке не вызывается). История пишется в дополнение,
  без изменения привычного потока корзины.

### Экран истории (HIST-03)
- **D-04:** Отдельная страница `/catalog/[secret]/orders` — по образцу
  `app/catalog/[secret]/cart/page.tsx` (та же структура «шапка + список + sticky-низ»).
  Чистый задел под полноценный экран «Мои заказы» в v1.5.
- **D-05:** Точка входа — **ссылка со страницы корзины** (например, «← Мои отправленные
  заказы» в шапке корзины). Важно: ссылка должна быть видна и при **пустой** корзине (блок
  пустой корзины в `cart/page.tsx` сейчас рендерит только «Корзина пуста» + «Вернуться в
  каталог» — добавить туда же ссылку на историю). Корзина доступна из шапки всегда (CartIcon),
  поэтому отдельный пункт в шапке/настройках не нужен.
- **D-06:** Заголовок — **«Отправленные заказы»**. Нигде не использовать слова «статус»,
  «принято», «подтверждено», «в доставке» (инвариант вехи v1.4). Каждая запись честно
  означает «что я отправил».

### Форма снимка заказа (HIST-01)
- **D-07:** Хранить **урезанный снимок** позиции, не целый `Product`. Поля позиции:
  `id` (товара), `name`, `quantity`, `priceAtOrder`, `unit`, `imageUrl`.
- **D-08:** `priceAtOrder` — это **эффективная цена**, которую видел клиент:
  `effectivePrice(product, priceForm)` с учётом +5% на Ефимову (форма «1»). Не «сырая» цена
  из таблицы. Текст заказа и история должны совпадать по цифрам.
- **D-09:** `id` товара сохраняется специально как **задел под «Повторить заказ»** (v1.5):
  по нему позже можно заново добавить позиции в корзину и подтянуть актуальные цены/остатки.
- **D-10:** `imageUrl` сохраняется в снимке — для мини-фото в списке истории (узнаваемость,
  как в корзине; работает офлайн через кэш фото v1.3).
- **D-11:** Поля уровня заказа: `total` (итоговая сумма по `priceAtOrder`), `createdAt`
  (дата-время), `channel` (`telegram` | `max`). Уникальный идентификатор записи — на
  усмотрение исполнителя (см. Discretion).

### Очистка и устойчивость (HIST-04)
- **D-12:** Очистка — **«Очистить всё»** (с подтверждением, как кнопка «Очистить» в корзине)
  **плюс** удаление **отдельной записи**.
- **D-13:** **Потолок 20 заказов.** При превышении старые записи тихо вытесняются (FIFO,
  удаляется самый старый). Обоснование пользователя: ~1 заказ в неделю → ~полугода истории,
  более чем достаточно; страховка от разрастания `localStorage`.
- **D-14:** **Мягкая деградация:** битая/неполная запись (повреждённый JSON, отсутствующие
  поля) не должна ломать отображение всего списка — отрисовывать валидные записи, битые
  пропускать/показывать заглушкой. Это технический инвариант, заложить в чтение/рендер.

### Claude's Discretion
- Имя ключа localStorage и форма хука/контекста (по аналогии с `catalog-cart`,
  `catalog-favorites`, `useCart`, `useFavorites`).
- Точный TypeScript-тип записи истории (`OrderHistoryEntry`) и расположение
  (`lib/useOrderHistory.ts` + тип рядом или в `lib/types.ts`).
- Способ генерации уникального id записи без `Date.now()`-зависимостей, если важна
  детерминированность; для рантайма обычный таймстамп/`crypto.randomUUID()` допустим.
- Точные тексты: пустое состояние («Вы пока не отправляли заказов» или похоже), формат
  строки заказа в списке (свёрнутая сводка дата+сумма+канал+N позиций с разворотом в позиции,
  либо плоский список) — подобрать в духе каталога, согласовать визуально на приёмке.
- Нужен ли провайдер-контекст (как `CartProvider`) или достаточно прямого хука на странице
  истории + точечной записи из `cart/page.tsx` — на усмотрение исполнителя.

</decisions>

## Existing Code Insights

### Reusable Assets
- `lib/useCart.ts` / `lib/useFavorites.ts` — **эталон** для хука истории: `useState` +
  `useEffect` (load при монтировании, save при изменении после `isLoaded`), тихий
  `try/catch` при недоступном localStorage (приватный режим). Копировать структуру.
- `app/catalog/[secret]/cart/page.tsx` — образец страницы (шапка с кнопкой «Очистить» +
  список с мини-фото 12×12 + sticky-низ). Страница `/orders` строится по тому же каркасу.
  Утилита `pluralItems(n)` (позиция/позиции/позиций) переиспользуема.
- `lib/pricing.ts` `effectivePrice(product, priceForm)` — цена «как видит клиент» (+5%
  Ефимова). Использовать при формировании снимка цены (D-08).

### Established Patterns
- localStorage-ключи вида `catalog-*` (`catalog-cart`, `catalog-favorites`).
- Подтверждение деструктивного действия через `confirm(...)` (кнопка «Очистить» корзины).
- Мини-фото товара: `<img object-contain>` 12×12 с onError-заглушкой (паттерн корзины).
- Офлайн-безопасность v1.3: новые данные читать из localStorage, без сетевых зависимостей
  при старте; не ломать standalone-PWA/safe-area.

### Integration Points
- `app/catalog/[secret]/cart/page.tsx` — `TelegramButton.handleSend` и
  `MaxOrderButton.handleSend`: после сборки текста заказа добавить запись в историю (D-01),
  канал по кнопке (D-02), цены через уже используемый `effectivePrice` (D-08).
- Блок пустой корзины в том же файле — добавить ссылку на `/orders` (D-05).
- `app/catalog/[secret]/` — новая папка `orders/page.tsx`.
- Возможно `app/catalog/[secret]/layout.tsx` — если для истории заводится провайдер
  (Discretion); иначе хук используется точечно.

<specifics>
## Specific Ideas

- Терминология честная: «Отправленные заказы», «что я отправил» — НИКОГДА «статус»/«принято»/
  «в доставке» (инвариант v1.4, HIST-03).
- Цены в истории = ровно те, что видел и отправлял клиент (effectivePrice с формой цен).
- Прицел на v1.5: снимок несёт `id` товара именно ради будущей кнопки «Повторить заказ».
- Лимит 20 записей — из реальной частоты ~1 заказ/неделю у клиента.

</specifics>
