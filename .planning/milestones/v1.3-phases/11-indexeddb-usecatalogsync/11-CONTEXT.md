# Phase 11: Слой данных (IndexedDB + useCatalogSync) - Context

**Gathered:** 2026-06-12
**Status:** Ready for planning

<domain>
## Phase Boundary

Этап превращает витрину каталога из «работает только при сети» в «работает офлайн». Товары, цены, остатки, бейджи и поля навигации (раздел/подгруппа) сохраняются в IndexedDB на устройстве агента и переживают закрытие вкладки/приложения. При офлайн-запуске каталог открывается из локального хранилища; навигация по разделам и подгруппам, поиск и фильтры работают по ранее загруженным данным. Источник данных витрины переводится с серверной отрисовки (SSR) на клиентский хук `useCatalogSync`. После первой успешной синхронизации вызывается `navigator.storage.persist()`.

**Требования этапа:** OFF-01 (офлайн весь каталог), OFF-02 (офлайн навигация/поиск/фильтры), OFF-03 (надёжное хранилище IndexedDB, переживает закрытие).

**Вне этого этапа** (см. Deferred Ideas): полоска офлайн-статуса и индикатор свежести — этап 12; офлайн-корзина и блокировка кнопки отправки — этап 12; кэширование/diff фото и кнопка «Обновить» — этап 13; install prompt — этап 14.

<decisions>
## Implementation Decisions

### Стратегия синхронизации и свежесть данных
- **D-01:** При открытии онлайн — стратегия «мгновенно из памяти + тихое обновление» (stale-while-revalidate): сначала показать данные из IndexedDB (мгновенный рендер), параллельно сделать `fetch("/api/products")` и бесшовно подменить результатом. Выбор обоснован тем, что прайсы обновляются раз в день — кэш в течение дня почти всегда идентичен серверу, поэтому фоновое обновление практически незаметно, а выигрыш в скорости на слабой мобильной сети большой. Подмена данных не должна сбрасывать позицию прокрутки и открытые фильтры/раздел/подгруппу (бесшовно для агента).

### Загрузочные и пустые состояния
- **D-02:** Первая загрузка (IndexedDB ещё пуст, идёт `fetch`) — показывать **скелетон-карточки**: серые контуры карточек в сетке витрины с лёгким мерцанием. Не спиннер, не пустой экран. Причина: агент часто на слабой сети — скелетон даёт честный сигнал «грузим», экран не выглядит сломанным, и он в стилистике существующей сетки карточек.
- **D-03:** Офлайн без данных (IndexedDB пуст И сети нет — агент установил приложение, но ни разу не открывал онлайн) — показывать **дружелюбное сообщение с подсказкой действия**, смысл: «Каталог ещё не загружен. Подключитесь к интернету один раз — дальше он будет работать и без сети». Иконка, спокойный тон, без технического жаргона. Как только сеть появится — каталог должен подтянуться сам (слушать событие `online`), без ручной кнопки и без перезапуска.

### Обработка ошибок загрузки
- **D-04:** Если сеть есть, но `/api/products` вернул ошибку (сбой сервера) — вести себя как при офлайне: показать данные из IndexedDB, если они есть; если хранилище пусто — то же дружелюбное сообщение (D-03). Технические ошибки агенту не показывать.

### Claude's Discretion
Чисто инженерные решения — планировщик/исполнитель определяют сами, у владельца тут нет продуктового видения:
- Формат IndexedDB: база `catalog-db`, stores `products` (Product[]) и `meta` (syncTimestamp, prevImageUrls — задел под этапы 12–13); доступ только через тонкую обёртку `lib/catalogDb.ts` на библиотеке `idb` (уже установлена в этапе 10).
- **Версионирование схемы базы**: при будущем изменении формата `Product` база должна аккуратно пересоздаваться через upgrade-колбэк `idb`, а не ломать каталог. Заложить с самого начала.
- Внутренняя логика хука `useCatalogSync` (порядок «читаем IDB → fetch → бесшовная подмена», флаги isOnline/syncedAt, отписки от событий).
- Вызов `navigator.storage.persist()` — после первой успешной синхронизации; на большинстве платформ происходит без диалога (по эвристикам вовлечённости).
- Сохранение `syncTimestamp` в `meta` — само время сейчас нигде не отображается (индикатор — этап 12), но пишем уже на этом этапе.
- Точные тексты сообщений, визуал скелетона и иконки — в рамках существующего стиля витрины.

## Existing Code Insights

### Reusable Assets
- `components/CatalogView.tsx` — уже клиентский компонент (`"use client"`), принимает `products: Product[]` пропом. Переход минимальный: сделать проп опциональным и при его отсутствии брать данные из `useCatalogSync()`. Навигация (раздел/подгруппа), поиск и фильтры уже работают по массиву `products` в памяти — значит офлайн-навигация (OFF-02) получается автоматически, как только массив приходит из IndexedDB.
- `lib/types.ts` — тип `Product` (name, price, stock, badge?, imageUrl?, description?, category?, subgroup?, section?). Этот же объект сохраняется в IndexedDB как есть.
- `idb` — библиотека уже установлена в этапе 10; обёртку IndexedDB строить на ней.
- `app/sw.ts` — service worker уже перехватывает `/api/products` (NetworkFirst) и Cloudinary (CacheFirst, каркас). IndexedDB — второй, более надёжный слой поверх этого.

### Established Patterns
- `app/catalog/[secret]/page.tsx` — серверный компонент: проверяет `params.secret !== process.env.CATALOG_SECRET → notFound()`, затем `const products = await getProducts()` и `<CatalogView products={products} initialMode={...} />`. **Проверка секрета остаётся на сервере** (безопасность). **Прокидывание `products` с сервера убирается** — иначе при офлайн-запуске массив пустой (force-dynamic не сериализует данные в HTML-шелл; анти-паттерн №2).
- Сервер уже фильтрует скрытые товары (`lib/sheets.ts`, этап 8) — в IndexedDB попадают только видимые товары; скрытие, применённое онлайн, у офлайн-агента отражается лишь после следующей синхронизации (ожидаемое поведение, D-04-сосед).

### Integration Points
- Новые файлы: `lib/catalogDb.ts` (единственное место с IndexedDB API), `lib/useCatalogSync.ts` (хук: чтение IDB → fetch → Product[] + isOnline + syncedAt).
- Точка стыковки: `CatalogView` начинает читать из хука; `page.tsx` перестаёт передавать `products`, но сохраняет проверку секрета и `initialMode` из `?filter=`.
- `initialMode` (режим Хит/Новинка из URL) сейчас приходит пропом из `page.tsx` — при рефакторинге сохранить этот путь (проп остаётся), меняется только источник `products`.
