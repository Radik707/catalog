**Статус:** Готов к планированию

<domain>
## Граница этапа

Веха v1.5 «Опыт клиента (телефон)», **только роль «Клиент»**. Чистый фронт: деплой = `git push` → Vercel, сервер daniella не затрагивается. Роль «Торговый» (планшет) этим этапом **не трогаем** — её шапка и вход остаются как сейчас.

**В рамках этапа (что делаем):**
1. **Разгрузка шапки клиента от дублей с нижними табами.** Сейчас у клиента сверху справа ♥ Избранное + ⚙ Настройки + 🛒 Корзина, а снизу — табы Каталог · Избранное · Корзина. ♥ и 🛒 дублируют табы. Убираем у клиента верхние ♥ и 🛒, оставляем только ⚙.
2. **Разделы (категории) — на первый план в шапке.** Освободившееся место отдаём ряду разделов из `CatalogNav` — это единственная по-настоящему ценная навигация в шапке (поиск + разделы = быстрый путь к нужному товару).
3. **Компактная точка быстрого повтора.** Над каталогом (для клиента, если есть история заказов) — одна ненавязчивая строка-кнопка «↻ Повторить последний заказ» → сразу кладёт позиции в корзину со честной сводкой (логика этапа 19).
4. **История поиска (SRCH-01).** Выпадающий список недавних запросов при фокусе на поле поиска; тап повторяет запрос; хранится локально (localStorage), офлайн-безопасно.

**Вне рамок этапа (явно):**
- **Отдельный экран-витрина «Главная»** с блоками Хиты/Избранное/Повторить как карточки-виджеты — **отвергнут** (B2C-паттерн, не нужен B2B-клиенту, который знает, что заказывает; риск «свалки»).
- **Блок «Недавно смотрели» (VIEWED-01)** — выкинут совсем: на витрине товар разглядывают не открывая карточку, отслеживание просмотров бессмысленно и шумно.
- **Подсказки по вводу / автокомплит по товарам (SRCH-02)** — вне MVP, только история запросов.
- Любые изменения опыта роли «Торговый».
- Серверные изменения, пайплайн прайсов, `force-dynamic`/`cache:"no-store"` витрины — не трогаем.
</domain>

<decisions>
## Решения реализации

### Форма этапа (ключевое)
- **D-01 — отказ от витрины-«Главной».** Отдельного стартового экрана с блоками-виджетами НЕ делаем. Каталог = главная. Причина (B2B-логика): клиент — владелец магазина, который уже знает, что заказывает; ему нужен быстрый путь (поиск + разделы + повтор), а не B2C-витрина для «разжечь интерес». Блоки Хиты/Избранное и так доступны (переключатель режима / таб Избранное) — дублировать их как виджеты = «свалка».
- **D-02 — HOME-01..03 переосмыслены.** HOME-01 (Главная с блоками) → «чистый вход клиента» (D-03..D-06). HOME-02 («блок ведёт в режим») → поглощено: повтор → корзина; Избранное/Хиты остаются доступны через табы/переключатель. HOME-03 (офлайн-безопасность) → **сохраняется в силе** для всего нового (D-09).

### Разгрузка шапки клиента
- **D-03 — верх справа у клиента: только ⚙ Настройки.** Убрать у роли `client` верхние ♥ Избранное (`HeaderPrimaryAction` → `FavoritesIcon`) и 🛒 Корзину (`CartIcon`) — они уже в нижних табах. Оставить только кнопку настроек (⚙). Роль `sales` — **без изменений** (у неё `HeaderPrimaryAction` = ↻ SyncButton, корзина сверху остаётся; нижних табов у sales нет).
- **D-04 — разделы на первый план.** Освободившееся место в шапке отдать ряду иконок разделов (`CatalogNav`). Точная компоновка (как ужать/перенести переключатель режима «Каталог/Хит/Новинка», чтобы разделы дышали) — на усмотрение исполнителя; цель — разделы видны и удобны, без тесноты с дублирующим «Каталогом».
- **D-05 — SSR-safe гейт.** Изменения шапки завязаны на роль → рендерить только после `ready` из `useRole` (нейтральный дефолт до монтирования), иначе мелькание/ошибка гидратации. Тот же паттерн, что в `HeaderPrimaryAction`/`BottomTabBar`.

### Быстрый повтор
- **D-06 — одна компактная строка «↻ Повторить последний заказ».** Над списком каталога (для `client`, после `ready`), показывается **только если история заказов непуста** (`useOrderHistory`). Тап → берёт последний заказ (`entries[entries.length-1]`), прогоняет через `classifyReorder` (этап 19) с текущим каталогом и формой цен, кладёт доступные позиции в корзину методом `addToCartWithQuantity`, показывает честную сводку («добавлено N; пропущено: нет в наличии / цена изменилась / товар больше недоступен») и ведёт «Перейти в корзину →». Если добавить нечего — честно сообщить, корзину не открывать. Это **один** элемент, не блок-витрина — закрывает главный B2B-сценарий (сейчас повтор спрятан на 3 тапа: Корзина → Мои заказы → Повторить).

### История поиска
- **D-07 — выпадашка при фокусе, только история.** При фокусе на поле поиска под ним — список последних запросов (ориентир 5–8). Тап по запросу подставляет его в поиск (повторяет). Без живых подсказок по товарам (это SRCH-02, вне MVP).
- **D-08 — хранение и управление.** История запросов — в localStorage (новый ключ, имя на усмотрение исполнителя в духе существующих: `catalog-*`), офлайн-безопасно. Запись запроса — при выполнении поиска (дедуп, свежие сверху, разумный потолок ~8–10, мягкая деградация битых данных как в `useOrderHistory`). Можно удалить отдельный запрос и/или очистить весь список — конкретный UX (крестик у пункта / «Очистить») на усмотрение исполнителя.

### Инварианты вехи v1.5 (нельзя сломать)
- **D-09 — офлайн-безопасность.** Всё новое (история поиска, строка повтора) читает данные из localStorage / IndexedDB (`useCatalogSync`) — без новых сетевых зависимостей на старте. `force-dynamic` + `cache:"no-store"` на витрине и `/api/products` НЕ трогать. Standalone-PWA + safe-area не ломать.
- **D-10 — роль SSR-safe.** Любые завязки на роль — только после `ready`; до монтирования нейтральный дефолт.
- **D-11 — история ≠ статус.** Нигде не вводить «статус/принято/подтверждено». Повтор оперирует «отправленными заказами» — это «что я отправил».

### На усмотрение Claude (детали реализации)
- Точная компоновка шапки клиента (как разместить разделы и переключатель режима после удаления дублей), визуальный вид строки «Повторить», тексты микрокопирайта и сводки повтора, вёрстка выпадашки истории поиска (список vs что-то ещё), имена новых файлов/ключей localStorage, точный потолок истории запросов и UX очистки — в пределах решений выше и стандартов кода (Tailwind, функциональные компоненты, комментарии на русском).
</decisions>

## Существующий код — выводы разведки

### Готовое к переиспользованию
- `classifyReorder` (`lib/reorder.ts`) — чистая функция, уже покрывает 4 исхода и кап по остатку (WR-04). Строка повтора D-06 = тонкая обёртка над ней.
- `addToCartWithQuantity` (`useCart`, этап 19) — кладёт нужное количество с капом по остатку; повтор использует его.
- `useOrderHistory` — `entries`, последний = `entries[entries.length-1]`; также идеальный образец localStorage-хука (FIFO, мягкая деградация) для истории поиска.
- `useRole` (`ready`) + паттерн «не рисуем до ready» (`HeaderPrimaryAction`, `BottomTabBar`) — готовый SSR-safe гейт для правок шапки.
- `useCatalogSyncContext` (`CatalogView`) — актуальные товары офлайн (IndexedDB) для матчинга повтора.

### Устоявшиеся паттерны
- Шапка `sticky top-0 z-50 bg-blue-600`; нижние табы `z-50` (только client, после ready); `InstallPrompt` `z-[60]` поверх.
- Поиск управляется родителем: `SearchBar` контролируемый, состояние `search` живёт в `CatalogView` (строка 31). История поиска должна согласоваться с этим потоком (запись запроса при поиске, чтение для выпадашки).
- Дублирование навигации у client (шапка ↔ табы) — известный долг, отложенный в этапе 18; этот этап его закрывает.

### Точки интеграции
- `layout.tsx` шапка (строки 60-67) — удаление дублей у client + приоритет разделов.
- `CatalogView`/`SearchBar` — строка повтора (над списком) + выпадашка истории поиска.
- Новые файлы: хук/утилита истории поиска (напр. `lib/useSearchHistory.ts`) + компонент строки повтора (или инлайн в `CatalogView`) — на усмотрение планировщика. Провайдеры роли/корзины/истории/синка уже подключены в layout — новых не нужно.

## Конкретные идеи

- Принцип владельца на весь этап: **«будь внимателен с ненужными обвесами и нагромождениями, чтобы каталог не превратился в свалку, где ничего не понятно»**. Каждый элемент должен оправдывать своё место; при сомнении — не добавлять.
- Повтор заказа — главный B2B-сценарий, но решается **одним** компактным элементом, а не блоком-витриной.
- Шапка клиента должна перестать дублировать нижние табы: сверху — то, чего нет внизу (разделы, поиск, настройки).
- Всё максимально нативно и привычно (нижние табы как у маркетплейсов; поиск с историей как у Ozon/WB), без нового визуального языка.
</specifics>
