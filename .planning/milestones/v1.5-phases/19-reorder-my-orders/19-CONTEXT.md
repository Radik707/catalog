## Связки в коде (источники правды для планировщика)

- **Корзина:** `lib/useCart.ts` (+ `components/CartProvider.tsx`). `addToCart(product)` добавляет только +1 и хранит **полный** `Product`. Для повтора нужного количества потребуется новый метод (см. D-05).
- **Форма цен:** `lib/pricing.ts` → `effectivePrice(product, form)` и `isEfimova()`. Форма цен читается из `localStorage["priceForm"]` (`"1"|"2"`, дефолт `"2"`), провайдер — `components/CatalogSettings.tsx` (`useCatalogSettings`).
- **Актуальный каталог (офлайн-источник):** товары на клиенте идут из IndexedDB через `useCatalogSync` / `CatalogSyncProvider` (витрина больше не получает товары с сервера; `force-dynamic` не трогать). Экран orders рендерится внутри `app/catalog/[secret]/layout.tsx`, где доступны провайдеры роли, настроек, корзины, синхронизации.
- **Нижние табы:** `components/BottomTabBar.tsx` — 3 равные вкладки (Каталог · Избранное · Корзина), `grid-cols-3`, рендер только для `role==='client'` после `ready` (SSR-safe).

## Решения реализации

### Механика повтора (ядро)
- **D-01 — чистый хелпер повтора.** Вынести логику в отдельный модуль `lib/reorder.ts` — чистая функция, которая принимает `OrderHistoryItem[]` (позиции прошлого заказа), текущий список товаров каталога и `priceForm`, а возвращает структурированный результат: для каждой позиции — исход (`added` / `price_changed` / `out_of_stock` / `unavailable`), сопоставленный текущий `Product` (если найден), актуальную эффективную цену и старую цену из снимка. Без побочных эффектов → легко тестировать и переиспользовать на «Главной» (этап 20).
- **D-02 — матчинг по id, фолбэк по имени.** Сопоставление позиции истории с текущим каталогом: сначала по `OrderHistoryItem.id === Product.id`; если не найдено — фолбэк по нормализованному имени (trim + lower + схлопывание пробелов). Ключ хрупкий (инвариант вехи) — при отсутствии совпадения исход `unavailable` («товар больше недоступен»), без молчаливой подмены.
- **D-03 — цена и наличие только актуальные.** Цена при повторе = `effectivePrice(currentProduct, priceForm)` (учитывает +5% Ефимовой через форму `"1"`), наличие = текущий `currentProduct.stock`. Замороженный `priceAtOrder` из истории НЕ используется для добавления — только для сравнения «было → стало».
- **D-04 — четыре честных исхода + порог наличия.** Классификация позиции:
  - найдена, в наличии, цена не изменилась → `added` (добавляем молча);
  - найдена, в наличии, цена отличается от `priceAtOrder` → `price_changed` (добавляем, помечаем «цена изменилась: было X → стало Y»);
  - найдена, но не в наличии → `out_of_stock` («нет в наличии», НЕ добавляем). Порог «нет в наличии» = `stock <= 1` (тот же порог скрытия товаров, что на витрине каталога);
  - не найдена в каталоге → `unavailable` («товар больше недоступен», НЕ добавляем).

### Корзина
- **D-05 — метод добавления с количеством.** Добавить в `useCart` (и пробросить через `CartProvider`) метод повтора, кладущий товар в нужном количестве, капнутом по текущему остатку (`Math.min(qty, stock)`), поверх существующего потока localStorage. Если товар уже в корзине — увеличить количество на `qty` (с тем же капом по остатку), не сбрасывая текущее. Существующий `addToCart` (+1) не ломать.

### UI повтора (на экране «Мои заказы»)
- **D-06 — кнопка «Повторить» на карточке заказа.** Каждая карточка в `orders/page.tsx` получает кнопку «Повторить» — повтор в один тап. Доступна в обеих ролях (безвредна), но экран нацелен на клиента.
- **D-07 — понятный результат повтора.** После тапа — компактная сводка результата (модалка/инлайн-панель на экране заказов): «Добавлено N товаров» + список пропущенных/изменённых с причиной (нет в наличии / цена изменилась / товар больше недоступен) и кнопка «Перейти в корзину →». Если добавить нечего (все позиции недоступны) — честно сказать об этом, корзину не открывать.

### Вход на экран (REORD-04)
- **D-08 — вход через меню и корзину, без 4-й вкладки.** Нижние табы остаются тремя (Каталог · Избранное · Корзина) — четвёртая вкладка перегружает узкий экран телефона. Вход на «Мои заказы» для клиента — через (а) заметную ссылку «Мои заказы» в шапке/низу страницы корзины и (б) пункт в `SettingsPanel` (меню «⚙»). Критерий REORD-04 явно допускает «из нижних табов **или меню»**. Это место оператор может пересмотреть после деплоя — если захочет именно вкладку, переведём табы на `grid-cols-4`.

### Инварианты вехи v1.5 (нельзя сломать)
- **D-09 — офлайн-безопасность.** Новый экран/логика читают данные из IndexedDB (`useCatalogSync`) и localStorage — без новых сетевых зависимостей на старте. `force-dynamic` + `cache:"no-store"` на витрине и `/api/products` НЕ трогать. Standalone-PWA + safe-area снизу не ломать.
- **D-10 — роль SSR-safe.** Любые завязки на роль (вход/табы/меню) — только после `ready` из `useRole`; до монтирования нейтральный дефолт, иначе ошибка гидратации.
- **D-11 — история ≠ статус.** Нигде не вводить слова «статус», «принято», «подтверждено», «в доставке». Экран остаётся «Отправленные заказы» — это «что я отправил», не подтверждение поставщика.

### На усмотрение Claude (детали реализации)
Точные тексты пометок и микрокопирайт, верстка сводки результата (модалка vs инлайн), имена новых функций/файлов в рамках D-01/D-05, оформление ссылок входа — на усмотрение исполнителя в пределах решений выше и стандартов кода (Tailwind, функциональные компоненты, комментарии на русском).

## Конкретные идеи

- Снимок позиции истории уже хранит `id` товара (`OrderHistoryItem.id`) — это задел под повтор, заложенный в этапе 16 (D-09 того этапа). Матчинг по id — основной путь, имя — фолбэк.
- Предлагаемая разбивка на планы (планировщик уточнит):
  - **План 19-01 — ядро повтора:** `lib/reorder.ts` (чистая классификация D-01..D-04) + метод повтора в `useCart`/`CartProvider` (D-05). Покрывает REORD-03.
  - **План 19-02 — UI и вход:** кнопка «Повторить» + сводка результата на `orders/page.tsx` (D-06, D-07), вход через корзину и меню (D-08). Покрывает REORD-01 (проверка/полировка существующего экрана), REORD-02, REORD-04.
  - Зависимость: 19-02 зависит от 19-01 (UI использует хелпер и метод корзины). Wave 1 = 19-01, Wave 2 = 19-02.
- Эффект повтора проверяется ПОСЛЕ деплоя на проде (Vercel) — у проекта нет локального dev для приёмки оператором.
</specifics>
