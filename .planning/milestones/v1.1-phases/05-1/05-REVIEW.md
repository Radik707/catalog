Что это значит: основная логика этапа корректна и протестирована. Но есть один блокер, который проявится при реальном прогоне нового формата 1С, и несколько мест, которые стоит укрепить до того, как этот код пойдёт в боевой деплой.

## Критические проблемы

### CR-01: Новый формат 1С отправляет ВСЕ товары в раздел «Прочее»

**Файл:** `scripts/upload.py:151-158`, взаимодействие с `scripts/upload.py:299-329` и `972-991`

**Проблема:** В новом формате 1С парсер `parse_new_format` жёстко проставляет `source_category = ""` (строка 327), потому что разделов-категорий в этом формате нет — группа определяется позже по текущему каталогу. Но `apply_structure_mapping` ищет раздел/подгруппу именно по `source_category`:

```python
cat = product["source_category"]   # для нового формата это ""
entry = category_index.get(cat)    # category_index.get("") → None
```

Пустая строка отсутствует в `category_index` (она строится только из категорий `structure_map.json`), поэтому КАЖДЫЙ товар нового формата попадает в `FALLBACK_SECTION = "Прочее"` / `FALLBACK_SUBGROUP = "Прочее"`. При этом `display_group` у него определён корректно (через `current_groups` или «Новинки»). В результате двухуровневая навигация для нового формата полностью нерабочая — весь каталог окажется в одном разделе «Прочее», хотя именно новый формат 1С заявлен как поддерживаемый (docstring, строки 3-5).

Дополнительно это «отравит» предупреждение D-12 (строки 981-989): сотни товаров и десятки категорий будут отрапортованы как «не покрыты structure_map.json», маскируя реальные пропуски.

**Почему критично:** некорректное поведение основной фичи этапа на одном из двух поддерживаемых входных форматов; владелец увидит сломанную навигацию после боевого прогона. Старый формат (с категориями в колонке A) при этом работает — поэтому дефект легко пропустить в `--dry-run` на старых файлах.

**Fix:** для нового формата структуру нужно выводить из уже определённой группы каталога, а не из пустой `source_category`. Вариант — после блока нового формата маппить через `display_group`, либо строить раздел/подгруппу из связки «группа → структура». Минимальный путь — резолвить структуру по той категории/группе, которую товар получил из текущего каталога:

```python
# В apply_structure_mapping использовать запасной ключ, когда source_category пуст:
cat = product["source_category"] or product.get("display_group", "")
entry = category_index.get(cat)
```

Но это требует, чтобы `category_index` умел искать и по имени группы (сейчас он построен только по именам категорий). Правильнее — явно решить на уровне дизайна, как структура определяется для нового формата (по `display_group` через отдельный индекс группа→раздел/подгруппа), и покрыть это тестом с товаром, у которого `source_category == ""`. Сейчас такого теста нет, поэтому регрессия не ловится.

## Предупреждения

### WR-01: Новый лист Google Sheet создаётся с 9 колонками, а данных 11

**Файл:** `scripts/upload.py:858-859`

**Проблема:** Заголовок теперь содержит 11 колонок (добавлены «Подгруппа» и «Раздел», строки 726-732), но при создании отсутствующего листа явно задаётся `cols=9`:

```python
worksheet = spreadsheet.add_worksheet(title=sheet_name, rows=len(rows) + 10, cols=9)
```

После этого `worksheet.update(rows, ...)` (строка 868) при записи диапазона шире сетки в gspread обычно расширяет лист автоматически, но опираться на это не стоит: на разных версиях gspread/Sheets API запись за пределы объявленных столбцов может выбросить ошибку диапазона или молча обрезать две новые колонки. На существующем листе путь идёт через `clear()` (число столбцов сохраняется со старого листа = 9 после прошлых прогонов), что усугубляет риск. Логика `resize` ниже трогает только строки (`rows=...`), столбцы не расширяет.

**Почему важно:** возможна потеря данных новых колонок именно того, ради чего сделан этот этап, причём на «чистом» листе — то есть при первом деплое.

**Fix:** считать число колонок из заголовка и расширять и строки, и столбцы:
```python
n_cols = len(rows[0])
worksheet = spreadsheet.add_worksheet(title=sheet_name, rows=len(rows) + 10, cols=n_cols)
...
if worksheet.col_count < n_cols:
    worksheet.resize(rows=max(worksheet.row_count, len(rows) + 10), cols=n_cols)
```

### WR-02: `apply_structure_mapping` падает с KeyError при отсутствии `source_category`

**Файл:** `scripts/upload.py:152`

**Проблема:** Доступ к `product["source_category"]` жёсткий, не через `.get`. Все внутренние парсеры этот ключ ставят, но функция публичная (вызывается из тестов напрямую и потенциально из другого кода). Один товар без ключа уронит весь прогон `KeyError`, без понятного сообщения. Сравните с `apply_group_mapping` (строка 493) — там та же хрупкость, но она уже существовала; новый код повторяет паттерн вместо того, чтобы быть устойчивее.

**Почему важно:** одна некорректная запись (например, из будущего источника данных) роняет весь батч-прогон вместо мягкой деградации в «Прочее», что противоречит заявленному принципу D-12 «ничего не теряется молча».

**Fix:**
```python
cat = product.get("source_category", "")
```
Тогда отсутствующий ключ попадёт в fallback «Прочее» так же, как пустая строка.

### WR-03: Предпросмотр `--dry-run` дважды линейно сканирует все товары по каждой категории

**Файл:** `scripts/upload.py:1026-1043`

**Проблема:** Во вложенном цикле по разделам/подгруппам/категориям на каждую категорию выполняется полный проход по `all_products`:
```python
for cat in categories:
    cat_count = sum(1 for p in all_products if p["source_category"] == cat)
```
При ~935 товарах и 121 категории это десятки тысяч сравнений на каждый dry-run. Производительность вне scope v1, но здесь это ещё и риск корректности: счётчик по категории не совпадает с реальной группировкой при новом формате (см. CR-01, где `source_category` пуст), из-за чего предпросмотр покажет нули там, где товары реально есть, и владелец сверит по неверным данным.

**Почему важно:** dry-run заявлен как инструмент сверки владельцем перед боевым прогоном (docstring, строки 11-12); если он показывает не то, что реально запишется, доверие к проверке теряется.

**Fix:** один раз собрать `Counter` по `source_category` перед циклом и брать значения из него; и убедиться, что источник счётчика согласован с тем, как реально проставляется раздел (после фикса CR-01).

### WR-04: Устаревшая константа `cols=9` и комментарий «117 категорий» расходятся с фактом

**Файл:** `scripts/test_structure_map.py:6` (docstring) и `scripts/upload.py:859`

**Проблема:** Docstring теста утверждает «Полное покрытие всех 117 категорий», но фактически в обеих картах 121 категория (проверено). Тест `test_полное_покрытие` сравнивает множества и пройдёт при любом числе, поэтому неверный комментарий не ловится. Это вводит в заблуждение будущего сопровождающего относительно ожидаемого размера контракта.

**Почему важно:** не баг исполнения, но расхождение документации с данными в контрактном файле, который должен быть источником истины.

**Fix:** обновить число в docstring до 121 либо убрать конкретное число; рассмотреть отдельный тест-ассерт `assert len(category_map) == 121`, чтобы цифра проверялась, а не только присутствовала в комментарии.

## Информационные замечания

### IN-01: Локальный `import re as _re` внутри функции

**Файл:** `scripts/upload.py:564`

**Проблема:** В `_build_url_index` локальный импорт `re` под алиасом `_re`, хотя `re` уже импортирован на уровне модуля (строка 26). Лишний импорт, маскирующий уже доступное имя.

**Fix:** удалить локальный импорт и использовать модульный `re`.

### IN-02: Магические числа fallback-сортировки продублированы

**Файл:** `scripts/upload.py:148` и `scripts/upload.py:978`

**Проблема:** Кортеж `(9999, 9999, 9999)` задан и в `apply_structure_mapping` (как `FALLBACK_SORT`), и повторно литералом в `main()` при сортировке `key=lambda p: p.get("_sort_key", (9999, 9999, 9999))`. При изменении одного значение разъедется.

**Fix:** вынести в модульную константу, например `FALLBACK_SORT_KEY = (9999, 9999, 9999)`, и использовать в обоих местах.

### IN-03: `is_header_row` принимает неиспользуемый параметр `a`

**Файл:** `scripts/upload.py:185-189`

**Проблема:** Функция объявлена с тремя параметрами `(a, b, c)`, но `a` не используется. Не баг (симметрия с `is_category_row`), но мёртвый параметр стоит пометить `_` или убрать для ясности.

**Fix:** переименовать в `_a` либо убрать, если симметрия сигнатур не нужна.
