## Ключевые риски v1.6

- **Ветвление по роли, не по устройству:** весь новый UI вехи включается по `role==='sales'`; до монтирования — нейтральный дефолт (SSR-safe, паттерн `useRole`/`useDeviceClass`), иначе ошибка гидратации. Новые блоки рендерятся только после `ready`.
- **Не задеть клиента:** нижние табы, «Повторить заказ», «Мои заказы», история поиска роли «Клиент» (v1.4/v1.5) остаются как есть. Quick-order, наличие числом, режим показа, корзина по поставщику — только роль «Торговый».
- **force-dynamic:** не добавлять ISR/кэш на витрину и `/api/products` — сломает живое управление из админ-панели (грабля этапа 8).
- **Офлайн-совместимость:** новые экраны (быстрый набор, наличие, корзина по поставщику) читать офлайн-безопасно (IndexedDB/localStorage), без сетевых зависимостей при старте; standalone-PWA + safe-area не ломать (как в этапе 14).
- **Чистый фронт:** вся веха — git push → Vercel; серверную часть daniella (upload.py/admin.py/max_bot.py) не трогаем; структурированный текст заказа по поставщику формируется на фронте перед deep-link Telegram/MAX.
- **Кап по остатку (этап 21):** прямой ввод количества не должен позволять заказать больше `stock`; согласовать с правилом скрытия остатка ≤1 (этап 22) — нет двусмысленности.
- **Надёжность данных о фасовке (этап 21):** кратность упаковки строится на существующих ~40 правилах фасовки — расширить аккуратно, иначе неверный шаг «+1 блок/коробка».
- **Производительность (этап 21):** ~800 строк с прямым вводом — виртуализацию вводить только при реальных тормозах.
