# Мастер-план: разделение двух аудиторий + B2B-удобство

> Дата: 2026-06-26 · Источник: `.planning/ozon-research-and-split.md` (исследование Ozon/WB + стратегия разделения)
> Тип: мастер-дорожная карта на 3 вехи (v1.4 → v1.5 → v1.6). Детальные PLAN.md по каждому этапу
> создаются в его собственном чате через `/gsd-plan-phase N` — здесь зафиксированы цель, критерии
> успеха, зависимости и набросок задач.

---

## 1. Большая идея (зачем всё это)

У каталога **два разных пользователя с разными целями**:
- **Торговый** (планшет ≥7.5″): быстрый набор крупных заказов, показ товара клиенту, наличие, скорость.
- **Клиент — владелец магазина** (телефон): открыть/повторить заказ, избранное, понятность, доверие.

Сейчас разделение лёгкое и «спрятанное» — по типу устройства (`lib/useDeviceClass.ts`). Этого мало.
Мастер-план делает разделение **правильным и глубоким**: вводит явную **роль** поверх устройства, а
дальше выстраивает под каждую роль свой стартовый экран, навигацию и флоу заказа. Параллельно закрывает
самый недооценённый разрыв B2B — **отсутствие истории и повторного заказа**.

**Принцип архитектуры (из отчёта, §5):** не два кодовых дерева и не два маршрута, а **роль + два пресета
UI поверх общего ядра**. Устройство — лишь дефолт-эвристика. Это ложится в будущую многоаккаунтность
(роль → свойство аккаунта в v2.0/Supabase).

## 2. Карта вех

| Веха | Название | Этапы | Для кого | Суть |
|---|---|---|---|---|
| **v1.4** | Фундамент разделения + быстрые победы | 15, 16, 17 | Обе | Роль, история заказов, сортировка, стикеры акций — на этом стоит всё остальное |
| **v1.5** | Опыт клиента (телефон) | 18, 19, 20 | Клиент | Нижние табы, «Повторить заказ», «Мои заказы», стартовая «Главная» |
| **v1.6** | Опыт торгового (планшет) | 21, 22, 23 | Торговый | Quick-order набор, кратность упаковки, наличие, корзина по поставщику |
| **отложено** | Задел под Track A / v2.0 | — | — | Стабильный SKU, сканер ШК, шаблоны заказа по клиенту (зависят от SKU и многоаккаунтности) |

**Почему именно так бьётся:**
- v1.4 — **enabling-слой**. Без роли (15) нельзя по-разному вести себя для двух аудиторий; без истории
  заказов (16) невозможны «Повторить» и «Мои заказы». Сортировка и стикеры (17) — дешёвые победы, полезны
  всем сразу.
- v1.5 и v1.6 — независимые ветки опыта поверх общего фундамента. Их порядок — **продуктовое решение
  владельца** (см. §6, развилка). По умолчанию рекомендую v1.5 (клиент) раньше: «Повторить заказ» —
  самый высокий ROI из всего отчёта.

**Связь с отчётом (трассируемость).** Каждый этап закрывает конкретные пункты `ozon-research-and-split.md`:
O1–O6 (общее), C1–C6 (клиент), T1–T7 (торговый). Маркеры проставлены в каждом этапе.

## 3. Как это исполнять через GSD

1. Веха стартует командой `/gsd-new-milestone` — она обновит `PROJECT.md`, заведёт `vX.X-ROADMAP.md` и
   `vX.X-REQUIREMENTS.md`. В мастер-плане уже всё для этого есть (цели, критерии, требования-маркеры).
2. Каждый **этап** — отдельный чат: `/gsd-plan-phase N` (детальный план с задачами) → проверка →
   `/gsd-execute-phase N` (выполнение группами задач) → `/gsd-verify-work`.
3. Деплой: фронт (Next.js) — `git push` → Vercel сам. Серверная часть (daniella: upload.py, admin.py,
   max_bot.py) — **только через субагента sysadmin**. Большинство этапов мастер-плана — **чистый фронт**
   (deploy = git push), серверного касания почти нет.

## 4. Веха v1.4 — Фундамент разделения + быстрые победы

**Цель вехи:** каталог знает, кто за экраном (роль), помнит отправленные заказы и даёт базовую
сортировку/мерч — фундамент, на котором строятся обе ветки опыта.

### Этап 15 — Роль «Торговый / Клиент» поверх устройства

> Закрывает: **O1**. Разблокирует: все последующие этапы.

**Цель:** в каталоге есть явная роль (`sales` | `client`), которая по умолчанию вычисляется из устройства,
запоминается на устройстве и переключается вручную; все текущие ветвления по устройству переезжают на роль.

**Зависит от:** ничего (первый этап вехи).

**Тип:** чистый фронт (Vercel). Деплой = git push.

**Критерии успеха (что должно быть ПРАВДОЙ):**
1. При первом заходе роль выставляется по устройству: планшет → «Торговый», телефон/ПК → «Клиент».
2. Пользователь может вручную сменить роль в настройках; выбор сохраняется (localStorage) и переживает
   перезагрузку и работу офлайн.
3. Текущие device-ветвления работают через роль, а не через `useDeviceClass`: угловая кнопка карточки
   (стрелки vs ♥), главное действие в шапке (↻ Обновить vs ♥ Избранное), дефолтная плотность сетки.
4. Кейс «торговый зашёл с телефона» / «клиент с большого экрана» решается сменой роли — UI следует роли,
   не железу.
5. До монтирования (SSR) роль нейтральна — нет скачка верстки и ошибки гидратации (тот же приём, что в
   `useDeviceClass`).

**Набросок планов/задач:**
- **План 15-01 — ядро роли.** `lib/useRole.ts` (контекст + провайдер; дефолт из `useDeviceClass`,
  persist в localStorage, SSR-safe); переключатель роли в `SettingsPanel`/`CatalogSettings`.
- **План 15-02 — миграция ветвлений.** Перевести `HeaderPrimaryAction`, угловую кнопку `ProductCard`,
  дефолт `gridPreset` с `isTabletLike` на `role`; оставить `useDeviceClass` как дефолт-эвристику внутри
  `useRole`. Сквозная проверка обоих режимов.

**Оценка усилий:** M. **Риск:** низкий (надстройка над существующим механизмом).

### Этап 16 — История отправленных заказов (локальная)

> Закрывает: **O2**. Разблокирует: C1 (Повторить), C4 (Мои заказы), задел под T6.

**Цель:** при отправке заказа (Telegram/MAX) каталог записывает его в локальную историю на устройстве
(что, сколько, на какую сумму, когда, каким каналом) — фундамент под «Повторить» и «Мои заказы».

**Зависит от:** ничего (можно параллельно с 15). Терминологически — «Отправленные заказы», не «статус».

**Тип:** чистый фронт (Vercel).

**Критерии успеха:**
1. После успешной отправки заказа (или открытия deep-link Telegram/MAX) заказ сохраняется в локальную
   историю: позиции (название, кол-во, цена на момент заказа), сумма, дата-время, канал.
2. История переживает закрытие вкладки и работает офлайн (localStorage; согласована с офлайн-моделью v1.3).
3. История не выдаёт себя за «статус заказа» — это «что я отправил», формулировки честные.
4. Есть программный доступ к истории (хук) для последующих экранов — без дублирования логики.
5. Граничные случаи: пустая история, очистка, защита от мусорных записей (по образцу `formatSyncTime`).

**Набросок планов/задач:**
- **План 16-01 — слой истории.** `lib/useOrderHistory.ts` (запись/чтение, localStorage-ключ
  `catalog-order-history`, тип `OrderRecord`); точка записи — в момент отправки в `cart/page.tsx`
  (и Telegram, и MAX). Решить (тех.вопрос, см. §6): локально или сразу сервер.

**Оценка усилий:** M. **Риск:** низкий. **Заметка:** локальная история теряется при смене телефона —
для пилота приемлемо; серверная история = задел под v2.0 (Supabase), решается на развилке §6.

### Этап 17 — Сортировка + мерч-стикеры

> Закрывает: **O3** (сортировка), **O4** (стикеры акций/зачёркнутая цена). Полезно обеим ролям.

**Цель:** на витрине появляется сортировка (название / цена ↑↓ / наличие) и стикер скидки/акции поверх
фото (+ зачёркнутая старая цена, если данные есть).

**Зависит от:** ничего (можно параллельно). Чисто визуально-логический слой.

**Тип:** чистый фронт (Vercel). Стикеры опираются на существующие бейджи (`badges.json`).

**Критерии успеха:**
1. На витрине есть выбор сортировки; по умолчанию — текущий порядок данных (раздел→подгруппа), сортировка
   применяется поверх группировки или плоско (продуктовое решение на этапе).
2. Сортировка по цене учитывает форму цен (+5% Ефимова) — порядок честный для выбранной формы.
3. Дефолт сортировки можно сделать роль-зависимым (торговый: наличие/название; клиент: цена/новизна) —
   через роль из этапа 15.
4. Товар с бейджем «акция»/скидкой показывает стикер в углу фото; если есть старая цена — она зачёркнута.
5. Поиск и фильтры (хит/новинка/избранное/разделы) продолжают работать вместе с сортировкой — ничего
   не сломалось.

**Набросок планов/задач:**
- **План 17-01 — сортировка.** Контрол сортировки (в шапке настроек/панели), логика сортировки в
  `CatalogView` поверх группировки; дефолт по роли.
- **План 17-02 — стикеры/цена.** Стикер акции поверх фото в `ProductCard`; зачёркнутая старая цена
  (если поле появится — иначе только стикер). Согласовать с приоритетом бейджей.

**Оценка усилий:** S–M. **Риск:** низкий. **Зависимость данных:** «старая цена» в прайсах сейчас нет —
зачёркивание включаем, только если решим завести поле; стикер акции работает уже сейчас.

## 5. Веха v1.5 — Опыт клиента (телефон)

**Цель вехи:** владелец магазина быстро открывает каталог, в один тап повторяет прошлый заказ, видит
свою историю и привычную «Главную» — минимум листания, максимум доверия.

### Этап 18 — Нижняя навигация (табы) для роли «Клиент»

> Закрывает: **C2**. (C5 — бейджи-счётчики — попутно.)

**Цель:** в роли «Клиент» появляется нижняя панель вкладок: Каталог · Избранное · Корзина (со
счётчиками). В роли «Торговый» нижних табов нет (антипаттерн для планшета — §6 отчёта).

**Зависит от:** этап 15 (роль).

**Тип:** чистый фронт (Vercel).

**Критерии успеха:**
1. В роли «Клиент» снизу видна панель с 3 вкладками (Каталог · Избранное · Корзина); активная вкладка
   подсвечена; большой палец дотягивается.
2. На вкладках «Избранное» и «Корзина» — бейджи-счётчики; стиль согласован с существующим счётчиком корзины.
3. В роли «Торговый» нижней панели НЕТ — навигация остаётся в шапке как сейчас.
4. Нижняя панель не перекрывает контент и плавающие кнопки (ContactFab, ScrollToTop) — отступы выверены.
5. Навигация работает офлайн и в standalone-PWA (safe-area снизу учтён, как в этапе 14).

**Набросок планов/задач:**
- **План 18-01 — компонент табов.** `components/BottomTabBar.tsx` (рендерится только при `role==='client'`),
  вкладки = маршруты/режимы каталога; счётчики из `useCart`/`useFavorites`; safe-area-inset-bottom.
- **План 18-02 — раскладка.** Согласовать с `layout.tsx`, ContactFab и ScrollToTop (отступы/z-index),
  проверить standalone и офлайн.

**Оценка усилий:** M. **Риск:** низкий-средний (раскладка/перекрытия — обычная возня вёрстки).

### Этап 19 — «Повторить заказ» + экран «Мои заказы»

> Закрывает: **C1** (повторить — топ-приоритет отчёта), **C4** (мои заказы).

**Цель:** клиент видит список отправленных заказов и в один тап повторяет любой (позиции подставляются в
корзину с проверкой актуальной цены/наличия).

**Зависит от:** этап 16 (история заказов), этап 15 (роль), желательно этап 18 (вкладка/вход к экрану).

**Тип:** чистый фронт (Vercel).

**Критерии успеха:**
1. Экран «Мои заказы» показывает историю (этап 16): дата, сумма, число позиций, канал; пустое состояние
   понятно оформлено.
2. Кнопка «Повторить» подставляет позиции прошлого заказа в корзину; недоступные/изменившиеся товары
   честно помечаются (нет в наличии / цена изменилась / товар исчез).
3. Цена при повторе берётся актуальная (с учётом формы цен), а не замороженная из истории — клиент не
   получит сюрприз в заказе.
4. «Повторить» доступно и из карточки заказа, и (опц.) кнопкой на «Главной» (этап 20).
5. Вход на экран — из нижних табов (роль «Клиент») или из меню; в роли «Торговый» экран доступен, но не
   навязывается.

**Набросок планов/задач:**
- **План 19-01 — экран истории.** `app/catalog/[secret]/orders/page.tsx` (читает `useOrderHistory`),
  карточка заказа, пустое состояние.
- **План 19-02 — повтор в корзину.** Логика «подставить в корзину» с матчингом по товару (по id/имени —
  с учётом хрупкости ключа, см. риски), пометки «нет в наличии / цена изменилась», пересчёт по форме цен.

**Оценка усилий:** M. **Риск:** средний — матчинг товаров из истории к текущему каталогу упирается в
хрупкий ключ (нормализованное имя). Это аргумент за ранний SKU (O6), но для MVP — мягкая деградация
(«товар больше недоступен»).

### Этап 20 — Стартовая «Главная» клиента + история поиска

> Закрывает: **C3** (главная), **O5** (история/подсказки поиска), **C6** (недавно смотрели — опц.).

**Цель:** в роли «Клиент» вход — это «Главная» с короткими путями (Повторить · Избранное · Хиты · поиск),
а не пустой полный каталог; поиск помнит недавние запросы.

**Зависит от:** этапы 15, 16, 19 (есть что показывать в блоках), 18 (табы).

**Тип:** чистый фронт (Vercel).

**Критерии успеха:**
1. В роли «Клиент» стартовый экран — «Главная»: блоки «Повторить последний заказ», «Избранное», «Хиты»
   + крупный поиск. В роли «Торговый» вход остаётся = полный каталог/поиск.
2. Каждый блок ведёт в соответствующий режим (избранное → fav, хиты → hit, повторить → корзина/заказы).
3. Поиск показывает недавние запросы и/или подсказки по началу ввода; история запросов локальна.
4. (Опц.) Блок «Недавно смотрели» — низкий приоритет, включается, если останется бюджет.
5. «Главная» работает офлайн (данные из IndexedDB), не ломает PWA/standalone.

**Набросок планов/задач:**
- **План 20-01 — экран «Главная».** `ClientHome` (рендер при `role==='client'` на входе), блоки-виджеты,
  маршрутизация в режимы.
- **План 20-02 — поиск-история.** История запросов в `SearchBar` (localStorage), подсказки по вводу.

**Оценка усилий:** M. **Риск:** низкий-средний (продуктовая компоновка «Главной» — твоя зона, обсудим вид).

## 6. Веха v1.6 — Опыт торгового (планшет)

**Цель вехи:** торговый набирает крупные заказы быстро (grid-ввод, кратность упаковки), ясно видит
наличие и комплектует заказ по поставщику; есть чистый режим «показать товар клиенту».

### Этап 21 — Quick-order режим набора + кратность упаковки

> Закрывает: **T1** (quick-order — главная боль торгового), **T2** (шаг кратно упаковке).

**Цель:** в роли «Торговый» есть плотный режим набора: строка товара с инлайн-полем количества (ввод с
клавиатуры, без флипа/галереи), шаг кратно упаковке (блок/коробка/ящик).

**Зависит от:** этап 15 (роль). Использует существующий `QuantityInput`, режим `list`.

**Тип:** чистый фронт (Vercel).

**Критерии успеха:**
1. В роли «Торговый» доступен режим «Быстрый набор»: плотные строки, в каждой — поле количества с прямым
   вводом числа и кнопками шага; добавление в корзину без перехода/флипа.
2. Шаг «+/−» и быстрые кнопки учитывают фасовку товара (за шт/блок/коробку/ящик) — меньше тапов и ошибок
   при опте.
3. Введённое количество мгновенно отражается в корзине и в итоге; ограничение по остатку соблюдается.
4. Режим не мешает клиенту: в роли «Клиент» он скрыт/не является дефолтом.
5. Производительность на ~800 строк приемлема (виртуализация — только если реально тормозит).

**Набросок планов/задач:**
- **План 21-01 — grid-набор.** Вариант строки витрины с инлайн-вводом (расширение `list`/`ProductCard`
  или отдельный `QuickOrderRow`); биндинг к `useCart`.
- **План 21-02 — кратность упаковки.** Парсинг фасовки в шаг количества (расширить существующие ~40
  правил фасовки); быстрые кнопки «+1 блок/коробка».

**Оценка усилий:** M–L. **Риск:** средний — надёжность данных о фасовке (см. вопрос в §7). Виртуализация
списка — потенциальный объём.

### Этап 22 — Наличие/остатки + режим «Показ клиенту»

> Закрывает: **T3** (явные остатки + фильтр наличия), **T5** (режим показа товара лицом).

**Цель:** торговый ясно видит остаток числом и фильтрует «в наличии»; одной кнопкой включает чистый
показ товара клиенту (крупное фото, без цен/служебного UI).

**Зависит от:** этап 15 (роль). Использует Lightbox и режим «без цен».

**Тип:** чистый фронт (Vercel).

**Критерии успеха:**
1. В роли «Торговый» остаток показан числом (а не только «есть/нет»); фильтр «только в наличии» работает
   поверх разделов/поиска.
2. Текущее правило скрытия товара с остатком ≤1 не конфликтует с новым отображением остатка (согласовать).
3. Кнопка «Показ клиенту» переводит в чистый режим: крупное фото (Lightbox), без цен и служебных кнопок;
   выход одним жестом.
4. Режим показа доступен в обеих ролях, но в роли «Торговый» — заметным действием (он показывает товар
   в магазине).
5. Цены в режиме показа скрыты независимо от настройки «С ценами» (чтобы случайно не показать клиенту
   закупочную цену).

**Набросок планов/задач:**
- **План 22-01 — наличие.** Отображение остатка числом (роль-зависимо), фильтр «в наличии» в панели/шапке.
- **План 22-02 — режим показа.** Кнопка-переключатель «Показ клиенту» (использует Lightbox/без-цен),
  принудительное скрытие цен.

**Оценка усилий:** S–M. **Риск:** низкий.

### Этап 23 — Корзина с разбивкой по поставщику

> Закрывает: **T4** (комплектация по поставщику, подытоги, минималка, комментарий).

**Цель:** в роли «Торговый» корзина группирует позиции по поставщику с подытогами; есть поле комментария
к заказу; (опц.) индикатор минимальной суммы по поставщику.

**Зависит от:** этап 15 (роль). Использует существующую корзину.

**Тип:** чистый фронт (Vercel). Текст заказа в Telegram/MAX — расширить группировкой.

**Критерии успеха:**
1. В роли «Торговый» корзина показывает позиции, сгруппированные по поставщику, с подытогом по каждому.
2. В роли «Клиент» корзина остаётся простой (плоский список + итог) — без разбивки.
3. К заказу можно добавить комментарий; он попадает в текст заказа Telegram/MAX.
4. Текст заказа для торгового структурирован по поставщику (подытоги + общий итог); для клиента — как
   сейчас.
5. (Опц.) Если у поставщика задана минималка — корзина подсвечивает недобор; данные минималок — отдельный
   источник (решается на этапе).

**Набросок планов/задач:**
- **План 23-01 — группировка корзины.** Группировка `cart/page.tsx` по `supplier` (роль-зависимо),
  подытоги; поле комментария.
- **План 23-02 — текст заказа.** Расширить формирование текста Telegram/MAX разбивкой по поставщику +
  комментарий; сохранить простой формат для клиента.

**Оценка усилий:** M. **Риск:** низкий-средний (минималки требуют данных — опционально).

## 9. Инварианты — что нельзя сломать (страховка для всех этапов)

- **`force-dynamic` + `cache: "no-store"`** на витрине и `/api/products` — любая новая ISR/кэш-обёртка
  снова сломает «живое» управление из админ-панели (грабля этапа 8).
- **Офлайн-модель v1.3:** новые экраны/данные читать офлайн-безопасно (IndexedDB/localStorage), не
  вводить сетевых зависимостей на старте; standalone-PWA + safe-area не ломать.
- **Роль и устройство SSR-safe:** до монтирования — нейтральный дефолт, иначе ошибка гидратации
  (как `useDeviceClass`).
- **Серверные операции — только через sysadmin.** Но почти все этапы мастер-плана — чистый фронт
  (deploy = git push); серверного касания минимум.
- **Любой индикатор «времени/свежести» — со своим тиком** (грабля этапа 12 — `OfflineBar`).
- **Новый тип правки (если появится) — во ВСЕ белые списки** (sheet_helper.py / upload.py / admin.py) —
  иначе правка молча теряется. (Актуально, только если этап затронет память правок.)
- **Не выдавать локальную историю за статус заказа** — это «что отправлено», не «что принято».
