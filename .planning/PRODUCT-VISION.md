# Видение продукта: приложение для торговых агентов (горизонт за пределами v1.2)

**Зафиксировано:** 2026-06-11
**Источник:** обсуждение с владельцем (Олег). Документ ведёт ВСЕ будущие вехи после v1.2.

## Большая цель

Полноценное приложение для торговых агентов и супервайзера фирмы «Вкусный Дом»: каталог для показа клиенту + набивка заявок + оффлайн-работа в полях. В перспективе — продукт, на который может перейти вся фирма (и потенциально продаваться другим фирмам).

## Развилка продукта: два трека на общем ядре (уточнено 2026-06-13)

Конечная картина — это НЕ один продукт, а **развилка из двух**, у которых общее ядро (каталог + данные + пайплайн обновления прайсов):

**Трек A — Приложение для торговых агентов (B2B).** Агенты ведут продажи магазинам через приложение: личный профиль, продажи и статистика по каждому агенту, набивка заявок, интеграция с 1С. Это «полное приложение для агентов» из основного видения ниже (многоаккаунтность → заявки → 1С → аналитика).

**Трек B — Розничный маркетплейс-агрегатор (B2C).** Тот же каталог, но как магазин для **розничных покупателей**: покупают по оптовым ценам с **минимальной суммой заявки**, доставка домой или в **пункт выдачи**. Наценка ~**+5–10%** (комиссия владельца); заказ оформляется **через владельца** (возможно через его ИП). Продвижение — **Telegram-каналы и паблики Мелитополя и Бердянска**.

**Развитие Трека B (уточнено 2026-06-13) — агрегатор нескольких дистрибьюторов:**
- В систему загружаются каталоги **5–6 дистрибьюторских фирм** (крупных и мелких).
- Система **сама сопоставляет одинаковые товары** между прайсами и **выбирает лучшую (самую дешёвую) актуальную цену**, выкладывает её на сайт.
- Покупатель всегда видит **лучшие цены от дистрибьюторов** и делает заявку. Позиционирование: «как Озон, но на 20–30% дешевле» — потому что это закупочные цены для магазинов (которые обычно наценивают и перепродают дороже).
- Владелец берёт себе **5–10% максимум** и занимается **доставкой/дистрибуцией напрямую от дистрибьютора к покупателю**.
- Модель снежного кома: раскачка через локальные сайты/паблики/Telegram Мелитополя и Бердянска.

**Ключевые риски этого трека (проверить ДЁШЕВО до большой стройки):**
1. **Согласие дистрибьюторов** — захотят ли они отдавать закупочные цены конечным покупателям (конфликт каналов: это подрывает их же клиентов-магазины). Это риск №1, бизнесовый, не технический.
2. **Экономика доставки + минимальный заказ** — опт обычно коробками/ящиками, розница хочет поштучно; наценка 5–10% на продуктах тонкая, последняя миля доставки может её съесть. Самая дорогая часть (Озон вкладывал в логистику миллиарды).
3. **Сопоставление товаров между прайсами** (тот же товар у разных дистрибьюторов под разными названиями/фасовками) — технически сложно (хуже текущей хрупкости normalize_name), но решаемо; нужен стабильный SKU/нормализация + ручной арбитраж спорных совпадений.
4. **Операционка** — сборка из нескольких источников, оплата, возвраты, налоги через ИП.

**Как проверять (lean, по-сеньорски):** не строить «Озон» сразу. Сначала пилот в одном городе с 1–2 дистрибьюторами и одним Telegram-каналом, минимальный заказ + самовывоз/пакетная доставка по дням (чтобы логистика окупалась). Текущий PWA-каталог уже годится как MVP-демка спроса. Сначала проверить: (а) согласятся ли дистрибьюторы, (б) сходится ли экономика доставки, (в) есть ли спрос — потом масштабировать.

**Детализация — в отдельной вехе.** Этот трек оформляется как самостоятельная веха через `/gsd-new-milestone`, когда дойдём (после оффлайна v1.3 и, вероятно, после базовой многоаккаунтности). Здесь — только видение, чтобы не потерять.

**1С — общая почва для обеих веток.** И агенты, и розница в перспективе завязаны на 1С (контрагенты, заявки/заказы). Владелец просит **заранее подготовить почву**, чтобы при появлении доступа к 1С перенос базы и интеграция шли быстро, а не переписыванием с нуля. Практический минимум groundwork (делать, когда дойдём, но держать в уме при изменениях схемы данных):
- **Стабильный идентификатор товара (артикул/SKU под коды 1С)** — вести опциональным полем заранее (expand-contract), т.к. сейчас товары ключуются по нормализованному названию (хрупко). К моменту интеграции маппинг «товар ↔ 1С» уже должен существовать.
- **Единая форма заказа/заявки**, переносимая в документ 1С (контрагент, позиции, количества, цены).
- Не завязывать критический путь на 1С — обе ветки должны работать и без неё.

## Подсистемы (что должно быть в итоге)

1. **Каталог-витрина (есть)** — клиент смотрит, набирает корзину, отправляет заявку. Сохраняем и оформляем как первоклассный продукт «интернет-магазин Вкусный Дом».
2. **Оффлайн-режим** — утром обновил, весь день работа без сети; разово подключился обновить и снова в поля. **ПРИОРИТЕТ №1.**
3. **Заявки в приложении** — торговый набивает заявку на магазин, выбирает контрагента (ИП) из базы клиентов.
4. **Канал заявок — Max (МАХ), персонально на каждого агента** — у торгового своя ссылка в профиле; заявка из корзины уходит в личку именно этого торгового (интеграция с Max или его ID). Раньше — Telegram, на одного владельца.
5. **Многопользовательский режим** — вход для торговых (логин/пароль); общий централизованный каталог + тонкий личный слой у каждого.
6. **Фото-модель «общая база + личные замены»** — оператор/супервайзер централизованно грузит базовые фото новых товаров → автоподтягиваются всем; каждый в своём кабинете может заменить не нравящееся фото на личное.
7. **Централизованное обновление каталога** — один главный админ (Олег) с главной панелью; операторы («девочки») грузят прайс по той же ссылке → у всех разом обновилось (ушло — скрылось, пришло — добавилось). Дальше каждый докручивает под себя.
8. **Интеграция с 1С** — контрагенты + выгрузка заявок в 1С операторам. **ВНЕШНЕ ЗАБЛОКИРОВАНО** (разрешение директора + feasibility у программиста 1С).
9. **Аналитика для админа** — что/сколько у кого продаётся, что докупать, планы закупок. Последняя по очереди.

## Ключевые архитектурные инсайты

- **Внутри фирмы каталог ЦЕНТРАЛИЗОВАН** (один источник прайсов, операторы владельца) → многопользовательность ЛЁГКАЯ: общий каталог + тонкий личный слой (скрытие, замены фото, заявки). «Парсер чужих прайсов» как проблема возникает ТОЛЬКО при продаже другим фирмам (далёкое будущее), не внутри «Вкусного Дома».
- **Оффлайн независим от аккаунтов** → делается ПЕРВЫМ, на текущем каталоге; даёт пользу в полях сразу и служит демкой для оценки спроса (готового продукта для презентации пока нет).
- **1С — НЕ критический путь.** Всё строить так, чтобы работало без неё; 1С подключается, когда созреет внешнее разрешение.
- **Заявки можно собирать в приложении до 1С** (выгрузка в 1С — позже).
- **Max-интеграция требует research-спайка** — есть ли у Max deep-link/бот-API как у Telegram. Если нет — fallback через ID/ручную отправку. Персональная маршрутизация на Max каждого агента = часть многопольз. вехи.
- **«Персональная ссылка + Max на каждого»** требует аккаунтов → это v2.0. На одном текущем каталоге возможен лишь простой свитч канала Telegram→Max на один ID.

## Предполагаемая последовательность вех

| Веха | Что | Зависимости / примечания |
|------|-----|--------------------------|
| **v1.2** (текущая) | Доделать этап 10 (десктоп-админка) | Почти готово |
| **v1.3 — Оффлайн (PWA)** | Каталог работает весь день без сети | ПРИОРИТЕТ №1; не заблокирован; станет демкой |
| **Магазин «Вкусный Дом» + Max** | Формализация текущего каталога как продукта; свитч канала Telegram→Max | Свитч на один ID — рано; «персонально на агента» — в v2.0. Нужен research Max |
| **v2.0 — Многоаккаунтность (внутри фирмы)** | Вход; общий каталог + личный слой (скрытие, перс. фото); перс. ссылка + Max-маршрутизация | Фундамент платформы; упрощён централизацией |
| **v2.x — Заявки в приложении** | Набивка заявок, выбор контрагента | Можно без 1С |
| **v3.0 — Интеграция с 1С** | Контрагенты + выгрузка заявок в 1С | Ждёт разрешения директора + программиста 1С |
| **v3.x — Аналитика для админа** | Статистика продаж, планы закупок | Зависит от заявок через приложение |

## Открытые вопросы (решить при старте соответствующих вех)

- **Max:** возможности API / deep-link — research-спайк перед вехой магазина/аккаунтов.
- **1С:** разрешение директора + feasibility у программиста 1С.
- **Монетизация:** для своей фирмы или продукт на продажу другим.
- **Хранилище/масштаб БД** при росте числа агентов (Google Sheets → реальная БД, рекомендация Supabase).
- **Этап 10 vs оффлайн:** доделывать ли десктоп-админку до оффлайна или оффлайн вперёд (уточняется с владельцем).
